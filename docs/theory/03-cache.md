# Кэш и быстрые структуры: Redis

**Роль:** ускоритель чтений и набор быстрых структур данных в памяти.
**Отвечает на вопрос:** как не ходить в базу за каждым чтением.

## Когда брать

- Профилирование показало горячие чтения одних и тех же данных, и база стала узким местом.
- Нужны структуры, которые неудобно делать в SQL: счётчики, rate limiting, лидерборды (sorted sets), распределённые блокировки с TTL, сессии.
- Данные можно потерять или восстановить из источника истины.

## Когда не брать

- «На всякий случай». Кэш — это вторая копия данных, а две копии всегда расходятся. Нет измеренной проблемы — нет кэша.
- Данные часто меняются и редко читаются: инвалидаций больше, чем попаданий.
- Нужна строгая консистентность чтений (баланс счёта при списании).
- Как основная база для данных, которые нельзя потерять. Redis умеет персистентность (RDB, AOF), но это не его сильная сторона.

## Redis vs альтернативы

| | Redis / Valkey | Memcached | in-process (map, ristretto) |
|---|---|---|---|
| Где живёт | отдельный процесс, общий для всех инстансов | отдельный процесс | в памяти каждого инстанса |
| Структуры | строки, хэши, списки, множества, sorted sets, streams… | только ключ-значение | что угодно |
| Персистентность | опционально | нет | нет |
| Инвалидация между инстансами | одна копия — инвалидируешь один раз | то же | нужно оповещать каждый инстанс |
| Цена промаха | сетевой hop | сетевой hop | ноль |

**Valkey** — форк Redis после смены лицензии в 2024. Протокол совместим, клиенты те же.

## Что важно понимать

### Стратегии кэширования

- **Cache-aside** (lazy loading): читаем кэш → промах → читаем базу → кладём в кэш. Так сделано в этом репо.
- **Write-through**: пишем в кэш и базу одновременно.
- **Write-behind**: пишем в кэш, в базу — асинхронно потом. Быстро, но можно потерять данные.

### Инвалидация — самая сложная часть

> There are only two hard things in Computer Science: cache invalidation and naming things.

При апдейте можно положить в кэш новое значение или удалить ключ. Удалить безопаснее: удаление идемпотентно и не может записать в кэш значение из транзакции, которая потом откатится.

Но даже удаление имеет гонку. Читатель промахнулся → прочитал **старую** строку из базы → писатель удалил ключ и закоммитил → читатель положил старую строку в кэш. Теперь кэш врёт до истечения TTL. TTL — это страховка, которая ограничивает время вранья.

### Кэш не должен ронять чтения

Redis недоступен — это промах, а не ошибка запроса. Декоратор логирует и идёт в базу.

### Thundering herd

Популярный ключ протух, и тысяча запросов одновременно пошла в базу. Лечится singleflight (`golang.org/x/sync/singleflight`), вероятностным ранним обновлением, блокировкой на заполнение.

### Декоратор

Кэш в этом репо — это `OrderRepository`, который оборачивает другой `OrderRepository`. Use case не знает, есть ли кэш. Кэш включается и выключается в `main.go`, а декоратор проходит тот же контракт-тест, что и обычный репозиторий.

## 🔎 Изучи сам

- cache-aside, read-through, write-through, write-behind
- cache stampede / thundering herd / dogpile; singleflight; probabilistic early expiration (XFetch)
- eviction policies: LRU, LFU, `maxmemory-policy` в Redis
- negative caching (кэшировать «не найдено»)
- hot keys, big keys
- Redis: однопоточная модель исполнения команд, pipelining, `MULTI/EXEC`, Lua-скрипты
- Redis persistence: RDB vs AOF, `appendfsync`
- Redis Cluster, hash slots; Redis Sentinel
- Redlock и почему Мартин Клеппман считает его небезопасным
- Valkey, KeyDB, Dragonfly
