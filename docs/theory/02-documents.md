# Документные базы: MongoDB

**Роль:** источник истины, когда данные естественно ложатся в документы.\
То есть когда «вещь» из предметной области удобно хранить одним куском со всеми вложенными частями, а не раскладывать по нескольким таблицам.

**Отвечает на вопрос:** как хранить агрегат целиком одним куском и читать его одним запросом.\
**Агрегат** — группа данных, которая живёт и меняется вместе: заказ со своими позициями, профиль пользователя со своими настройками.

## 1. Что такое документная база — коротко

**Шпаргалка раздела:**

| Слово | Что значит | Аналог в SQL |
|---|---|---|
| документ | один JSON-подобный объект со вложенными полями и массивами | строка |
| коллекция | набор документов | таблица |
| BSON | двоичный формат, в котором Mongo хранит документы | — |
| `_id` | обязательный уникальный идентификатор документа | primary key |
| ObjectID | тип `_id` по умолчанию: 12 байт со временем создания внутри | — |
| schema-on-read | схему проверяет код при чтении, а не база при записи | противоположность schema-on-write |

---

### Документ и коллекция

**MongoDB хранит данные документами.**\
Документ похож на JSON-объект: у него есть поля, а поля могут содержать вложенные объекты и массивы.

```js
{
  _id: ObjectId("65f1c2..."),
  name: "Куртка зимняя",
  price_cents: 499000,
  attrs: { size: "L", material: "полиэстер" },   // вложенный объект
  tags: ["зима", "распродажа"]                    // массив
}
```

**Документы лежат в коллекциях.**\
Коллекция — аналог таблицы, но без фиксированного набора колонок: два документа в одной коллекции могут иметь разные поля.

**Главное отличие от SQL: связанные данные можно положить внутрь документа.**\
Там, где реляционная база держала бы две таблицы и соединяла их `JOIN`, Mongo может хранить всё одним куском и читать одним запросом. Это называют **локальностью данных**.

---

### BSON — не совсем JSON

**Mongo хранит документы не в JSON, а в BSON (Binary JSON).**\
Это двоичный формат: компактнее для машины и с более богатыми типами, чем у обычного JSON.

**В BSON есть типы, которых нет в JSON.**\
Основные:

- целые числа `int32` и `int64` отдельно от дробных `double` — в JSON есть только «число»;
- `Decimal128` — точные десятичные числа, например для денег;
- `Date` — момент времени, хранится как число миллисекунд от 1970 года;
- `ObjectId` — идентификатор, о нём ниже;
- `Binary` — произвольные байты.

> ⚠️ **`Date` в BSON хранит время с точностью до миллисекунд.** Go-шный `time.Time` хранит наносекунды. Что из этого следует для нашего кода — 🤔 вопрос 7 задачи 04.

---

### `_id` и ObjectID

**У каждого документа есть поле `_id`.**\
Оно обязательное и уникальное в коллекции; по нему всегда есть индекс. Если не задать `_id` самому, драйвер сгенерирует ObjectID.

**ObjectID — 12 байт, собранных из трёх частей:**

| Байты | Что внутри |
|---|---|
| 4 | время создания в **секундах** |
| 5 | случайное значение, одно на процесс |
| 3 | счётчик, который растёт внутри процесса |

**Поэтому ObjectID растёт со временем, но только примерно.**\
Два ObjectID из разных процессов в одну и ту же секунду могут оказаться в любом порядке. Это важно в [разделе 8](#8-порядок-без-автоинкремента).

---

### Схема никуда не девается

**В реляционной базе схему проверяет база при записи — это schema-on-write.**\
Колонка объявлена `NOT NULL` — строка без значения просто не запишется.

**В Mongo по умолчанию схему проверяет код при чтении — это schema-on-read.**\
База примет любой документ, а разбираться, есть ли в нём нужное поле и того ли оно типа, будет читающий код.

**«Бессхемность» — иллюзия: схема просто переехала из базы в код.**\
Если через год в коллекции лежат документы трёх разных форм, каждое место в коде, которое их читает, должно уметь все три.

> Mongo умеет и проверять схему при записи: на коллекцию можно повесить валидатор `$jsonSchema`. По умолчанию он выключен.

---

### Лимит документа — 16 МБ

**Один документ не может быть больше 16 МБ.**\
Это жёсткая граница: документ, который её перерос, просто не запишется.

**Отсюда главное правило моделирования: не вкладывать то, что растёт без ограничений.**\
Подробно — в [разделе 4](#4-моделирование-вкладывать-или-ссылаться).

## 2. Когда брать, когда не брать

**Шпаргалка раздела:**

| Признак задачи | Что брать |
|---|---|
| ✅ агрегат читается и пишется целиком, связей между агрегатами мало | документную базу |
| ✅ у разных записей действительно разная форма | документную базу или `JSONB` |
| ✅ нужно шардирование «из коробки», и есть кому его эксплуатировать | документную базу |
| ❌ много связей и запросов «через» сущности | реляционную базу → [01](01-sql.md) |
| ❌ постоянно нужны транзакции между многими документами | реляционную базу |
| ❌ «не хотим думать о схеме» | это не причина: схема всё равно будет |

---

### ✅ Когда брать

#### 1. Агрегат читается и пишется целиком, а связей между агрегатами мало

**Типичный запрос — «дай этот объект целиком».**\
Профиль пользователя со всеми настройками, товар со всеми атрибутами — всё лежит в одном документе и читается одним обращением.

**Связей между агрегатами мало.**\
Если документы почти не ссылаются друг на друга, отсутствие `JOIN` не мешает.

#### 2. Форма данных действительно разная у разных документов

**Пример — каталог товаров.**\
У куртки есть размер и материал, у телевизора — диагональ и разрешение, у книги — автор и ISBN.

**В одной таблице это либо десятки пустых колонок, либо отдельная таблица «ключ–значение».**\
В документной базе каждый документ хранит только свои поля.

#### 3. Нужно горизонтальное шардирование «из коробки», и команда готова его эксплуатировать

**Mongo умеет сама раскладывать коллекцию по нескольким серверам.**\
В Postgres для этого нужны надстройки вроде Citus или ручное шардирование в коде ([01-sql, раздел 12](01-sql.md#шардирование)).

**Но шардированный кластер — это минимум около десятка серверов и отдельная инженерная работа.**\
Подробно — в [разделе 10](#10-шардирование).

---

### ❌ Когда не брать

#### 1. Много связей и запросов «через» сущности

**`$lookup` — это не `JOIN` ни по удобству, ни по скорости.**\
`$lookup` — стадия в aggregation pipeline, которая подтягивает документы из другой коллекции ([раздел 11](#11-change-streams-и-aggregation-pipeline)). Он работает как вложенный цикл: для каждого документа слева — поиск справа.

**Если соединения нужны в каждом втором запросе — это задача для реляционной базы.**\
Там `JOIN` — родная операция, и планировщик умеет выбирать для неё хороший способ выполнения.

> **Что брать:** реляционную базу → [01-sql](01-sql.md).

#### 2. Нужны сложные транзакции между многими документами постоянно

**Транзакции между документами в Mongo есть, но они дороже и с ограничениями.**\
Ограничения разобраны в [разделе 5](#5-атомарность-и-транзакции): нужен replica set, время жизни ограничено, а код внутри может выполниться несколько раз.

**Если почти каждая операция требует транзакции на нескольких документах — схема просится в реляционную базу.**\
Значит, данные на самом деле связаны, и документная модель с ними не совпадает.

#### 3. «Не хотим думать о схеме»

**Схема всё равно есть — просто она размазана по коду и неявна.**\
Она живёт в Go-структурах, в условиях `if field != nil`, в головах команды.

**Ошибки схемы переезжают из миграций в продакшен.**\
В SQL неудачная миграция падает при деплое. В Mongo документ «не той формы» тихо записывается, а падает код, который его потом читает.

## 3. Mongo vs Postgres + JSONB

**Частый реальный выбор — не «Mongo или SQL», а «Mongo или Postgres с `JSONB`-колонкой».**\
`JSONB` — колонка в Postgres, где лежит JSON, по которому можно искать и строить индексы ([01-sql, раздел 1](01-sql.md#4-jsonb--json-внутри-колонки)).

| | MongoDB | Postgres + JSONB |
|---|---|---|
| Модель | документ — единица хранения | строка + JSON-поле |
| Транзакции | на один документ — атомарно всегда; между документами — с 4.0, только на replica set | обычные ACID |
| Индексы по вложенным полям | нативно | GIN по `JSONB`, expression-индексы |
| Шардирование | встроено (mongos, config servers) | нет из коробки (Citus, ручное) |
| Автоинкремент | нет | есть |
| Связи и `JOIN` | `$lookup`, ограниченно | полноценные |
| Внешние ключи | нет | есть |

---

### Пояснения к таблице

#### 1. Транзакции

**В Mongo один документ меняется атомарно всегда, без всяких транзакций.**\
Обновил три поля одного документа — либо изменятся все три, либо ни одно.

**Транзакции между документами появились в версии 4.0 и работают только на replica set.**\
Что такое replica set — в [разделе 6](#6-replica-set-копии-и-выборы).

#### 2. GIN и expression-индексы

**GIN — индекс Postgres для вопроса «содержит ли».**\
Например, «найди строки, где в JSON есть `{"color": "black"}`».

**Expression-индекс — индекс по выражению, а не по колонке.**\
Например, `CREATE INDEX ON products ((attrs->>'size'))` — индекс по полю `size` внутри JSON.

#### 3. Внешние ключи

**В Mongo ссылка между документами — просто поле со значением.**\
Ничто не мешает записать ссылку на несуществующий документ или удалить документ, на который ссылаются.

**Значит, целостность ссылок становится задачей приложения.**\
И всех скриптов, которые ходят в эту базу.

---

### Когда хватит JSONB

**Если нужна гибкость атрибутов, но данные при этом связаны — сначала пробуй `JSONB`.**\
Общие поля — обычными колонками с внешними ключами и `CHECK`, «разное» — в одну `JSONB`-колонку.

**У `JSONB` есть цена.**

- Изменение одного ключа в JSON — это новая версия всей строки ([MVCC, 01-sql раздел 6](01-sql.md#6-mvcc-как-база-показывает-разным-транзакциям-разное)). Большой документ, который часто правят по одному полю, порождает много мусора для VACUUM.
- У планировщика нет статистики по содержимому JSON, поэтому планы по условиям на поля внутри бывают неудачными.

> **Практика:** то, по чему часто фильтруют, выносят в обычную колонку; в `JSONB` оставляют то, что читают целиком и меняют редко.

## 4. Моделирование: вкладывать или ссылаться

**Шпаргалка раздела:**

| Связь | Пример | Обычно |
|---|---|---|
| один-к-немногим, читаются вместе | пользователь → 2–3 адреса | **вкладывать** (embedding) |
| один-ко-многим, растёт | товар → сотни отзывов | **ссылаться** (referencing) |
| один-к-миллионам | устройство → все его события | **только ссылаться** |
| многие-ко-многим | товары ↔ категории | ссылаться, иногда с копией нужных полей |

---

### Два способа

#### Embedding — вложить в документ

**Связанные данные лежат внутри родительского документа.**\
Пример: адреса пользователя массивом прямо в документе пользователя.

```js
{ _id: 1, name: "Аня",
  addresses: [ { city: "Москва", street: "..." }, { city: "Казань", street: "..." } ] }
```

**Плюс — один запрос возвращает всё, и запись одного документа атомарна.**\
Транзакция не нужна: пользователь и его адреса меняются вместе одной операцией.

**Минус — данные дублируются, если их вкладывать в несколько мест.**\
Если вложить название категории в каждый товар, переименование категории перепишет тысячи документов.

#### Referencing — хранить отдельно и ссылаться

**Связанные данные лежат в другой коллекции, а в документе — только их `_id`.**\
Пример: в отзыве хранится `product_id`, а не весь товар.

```js
// товар
{ _id: 3, name: "Конфеты" }
// отзыв — отдельная коллекция
{ _id: 901, product_id: 3, text: "Вкусно", stars: 5 }
```

**Плюс — нет дублирования, и документы остаются маленькими.**\
Переименовать товар — одна операция.

**Минус — за связанными данными нужен второй запрос или `$lookup`.**\
И целостность ссылок держит приложение, а не база.

---

### Как выбирать

**Главный вопрос: что приложение читает и пишет вместе?**\
Что используется вместе — хранят вместе. Модель в Mongo строят от запросов, а не от «правильной» нормализации.

**Правила, которые помогают:**

1. **Читается почти всегда вместе с родителем → вкладывать.**
2. **Количество ограничено по природе (немного и не растёт) → вкладывать.**
3. **Растёт со временем без предела → ссылаться.** Комментарии к посту, сообщения в чате, события устройства.
4. **Нужно само по себе, без родителя, или из нескольких мест → ссылаться.**
5. **Меняется намного чаще или реже родителя → чаще ссылаться,** иногда копируя пару полей для быстрого чтения (денормализация).

> Почему позиции нашего заказа лежат внутри документа, а не отдельной коллекцией, — 🎤 вопрос задачи 04. Примерь правила выше.

---

### Антипаттерн: массив без ограничений

**Самая частая ошибка — держать растущий список внутри документа.**\
Например, все товары категории массивом внутри документа категории.

**Такой документ рано или поздно упрётся в 16 МБ.**\
А задолго до этого каждое чтение будет тянуть весь массив, а каждое добавление — переписывать весь документ.

> **Ориентир из практики:** если массив может вырасти больше нескольких сотен элементов или ~100 КБ, его выносят в отдельную коллекцию.

---

### Документ — это не доменная структура

**Структура с `bson`-тегами и `_id` — это деталь хранилища.**\
Она описывает, как данные лежат в Mongo: имена полей в базе, `_id` вместо `id`, типы BSON.

**Вешать `bson`-теги на `domain.Order` — значит пускать инфраструктуру в домен.**\
Правильно — отдельная структура документа внутри адаптера и функции-конвертеры «документ ↔ домен». Подробнее, чем это плохо, — 🤔 вопрос 5 задачи 04.

## 5. Атомарность и транзакции

**Шпаргалка раздела:**

| Что | Как |
|---|---|
| изменение одного документа | атомарно всегда, транзакция не нужна |
| изменение нескольких документов | multi-document транзакция, только на replica set |
| время жизни транзакции | по умолчанию 60 секунд, потом Mongo её отменяет |
| `WithTransaction` | сам повторяет твой callback при временных ошибках |
| `TransientTransactionError` | «временная ошибка, повтори всю транзакцию» |
| `UnknownTransactionCommitResult` | «не знаю, прошёл ли коммит, повтори коммит» |

---

### Один документ — атомарен всегда

**Любое изменение одного документа применяется целиком или никак.**\
Даже если одна операция меняет несколько полей и массив — промежуточного состояния никто не увидит.

**Изменения задаются операторами.**\
Основные:

- `$set` — записать значение поля;
- `$inc` — увеличить число на заданную величину;
- `$push` / `$pull` — добавить в массив / убрать из массива.

```js
// списать со склада 2 штуки и дописать запись в историю — атомарно, одной операцией
db.stock.updateOne(
  { _id: "sku-1", qty: { $gte: 2 } },                      // фильтр: только если хватает
  { $inc: { qty: -2 }, $push: { history: { op: "sold", n: 2 } } }
)
```

**Фильтр и изменение проверяются вместе, атомарно.**\
Если два запроса одновременно пытаются списать последние две штуки, обновится только один: второй уже не пройдёт фильтр `qty >= 2`. Результат операции говорит, сколько документов подошло под фильтр (`MatchedCount`) и сколько изменилось (`ModifiedCount`).

> Как этим же приёмом сделать optimistic locking — 🤔 вопрос 6 задачи 04.

---

### Транзакции между документами

**Чтобы атомарно изменить несколько документов, нужна multi-document транзакция.**\
Например, перенести товар в другую категорию и записать это в журнал изменений — две операции, которые должны пройти вместе.

#### 1. Транзакции требуют replica set

**Одиночный `mongod` не умеет multi-document транзакции.**\
`mongod` — это сам процесс сервера MongoDB. Транзакции работают только в replica set ([раздел 6](#6-replica-set-копии-и-выборы)) или в шардированном кластере.

**Поэтому даже в тестах поднимается replica set из одного узла.**\
Посмотри `testinfra.StartMongo`. Почему без replica set нельзя — 🤔 вопрос 1 задачи 04; подсказка — в разделе 6.

#### 2. Транзакция живёт в сессии

**В Mongo транзакция привязана к сессии (session).**\
Сессия — объект драйвера, который связывает несколько операций в одну логическую последовательность. Операция выполняется внутри транзакции, только если она выполняется в этой сессии.

> Как сессия попадает в операции внутри транзакции и чем это похоже на наш `txKey{}` в Postgres-адаптере — 🤔 вопрос 3 задачи 04.

#### 3. Ограничения

**Время жизни транзакции по умолчанию — 60 секунд.**\
Если транзакция открыта дольше, Mongo её отменяет.

**Транзакции в Mongo дороже, чем в Postgres.**\
Если задачу можно решить одной атомарной операцией над одним документом — так и делают.

---

### `WithTransaction` повторяет твой код

**Драйвер сам повторяет callback при транзиентных ошибках.**\
Транзиентная (transient) — значит, временная: конфликт записи с другой транзакцией, смена primary. Повторишь — скорее всего пройдёт.

**Ошибки, на которые он реагирует, помечены метками.**

- **`TransientTransactionError`** — транзакция не удалась по временной причине, её можно повторить целиком, с начала.
- **`UnknownTransactionCommitResult`** — коммит отправлен, но ответ не пришёл (например, оборвалась сеть). Неизвестно, прошёл ли он; повторяют сам коммит.

**Значит, всё внутри callback может выполниться несколько раз.**\
Это не редкий крайний случай, а обычная работа под нагрузкой.

> ⚠️ **Побочные эффекты вне базы внутри транзакции — ошибка.** HTTP-запрос, отправка в брокер, инкремент счётчика в памяти: при повторе всё это случится второй и третий раз, хотя в базе транзакция в итоге применится один раз.

## 6. Replica set: копии и выборы

**Шпаргалка раздела:**

| Слово | Что значит |
|---|---|
| replica set | группа серверов `mongod` с одними и теми же данными |
| primary | единственный узел, который принимает записи |
| secondary | узлы-копии, которые повторяют записи primary |
| oplog | журнал операций primary, по которому secondary догоняют его |
| election | выборы нового primary, когда старый недоступен |
| rollback | откат записей, которые старый primary не успел передать большинству |
| read preference | откуда читать: с primary или с secondary |

---

### Как устроен replica set

**Replica set — группа серверов, которые хранят одни и те же данные.**\
Обычная конфигурация — три узла: один primary и два secondary.

**Все записи принимает только primary.**\
Secondary — копии: они повторяют у себя всё, что записано на primary.

**Почему три, а не два: при сбое узлы голосуют, и нужно большинство.**\
Из трёх узлов большинство — два. Из двух узлов при падении одного большинства не набрать, и выбрать нового primary нельзя.

---

### Oplog — журнал операций

**Каждую успешную запись primary дописывает в специальную коллекцию — oplog (operations log).**\
Это журнал «что изменилось», похожий на WAL в Postgres ([01-sql, раздел 12](01-sql.md#wal-как-база-выполняет-обещание-d-из-acid)).

**Secondary читают oplog primary и применяют операции у себя.**\
Отставший secondary догоняет с той позиции, где остановился.

**У oplog фиксированный размер, и старые записи из него вытесняются.**\
Если secondary отстал так сильно, что нужных записей в oplog уже нет, ему придётся копировать все данные заново.

---

### Выборы и откат

**Если primary перестал отвечать, secondary устраивают выборы (election).**\
Побеждает узел с самым свежим oplog. Пока идут выборы — обычно секунды — записи не принимает никто.

**Записи, которые старый primary принял, но не успел передать большинству, откатываются (rollback).**\
Когда старый primary вернётся в группу, эти записи будут отменены. Клиенту же primary когда-то ответил «успешно».

> От этого защищает write concern `majority` — [раздел 7](#7-write-concern-и-read-concern).

---

### Read preference — откуда читать

**По умолчанию все чтения идут на primary.**\
Так ты всегда видишь самые свежие данные.

**Чтение можно направить на secondary — это называется read preference.**\
Основные режимы: `primary` (по умолчанию), `primaryPreferred`, `secondary`, `secondaryPreferred`, `nearest` (самый близкий по сети).

> ⚠️ Secondary отстаёт от primary. Прочитал с него сразу после своей записи — можешь её не увидеть. Это та же проблема read-your-writes, что и с репликами Postgres ([00-map, раздел 5.3](00-map.md#3-модели-согласованности)).

---

## 7. Write concern и read concern

**Шпаргалка раздела:**

| Настройка | Что гарантирует |
|---|---|
| `w: 0` | ничего: драйвер не ждёт ответа |
| `w: 1` | запись принял primary |
| `w: "majority"` | запись дошла до большинства узлов и не откатится |
| `j: true` | дополнительно: запись лежит в журнале на диске |
| read concern `local` | последнее, что есть на этом узле, даже то, что может откатиться |
| read concern `majority` | только то, что подтверждено большинством и не откатится |
| read concern `snapshot` | все чтения в транзакции видят один момент времени |
| read concern `linearizable` | самое строгое: увидишь все предыдущие подтверждённые записи |

---

### Write concern — когда запись считается успешной

**Write concern говорит драйверу, какого подтверждения ждать, прежде чем вернуть «успех».**\
Чем строже подтверждение, тем надёжнее запись и тем дольше она идёт.

**`w: 1` — подтвердил primary.**\
Быстро, но если primary упадёт до того, как запись дошла до остальных, она откатится при выборах ([раздел 6](#выборы-и-откат)). Клиент при этом уже получил «успех».

**`w: "majority"` — подтвердило большинство реплик.**\
Такая запись не откатится при смене primary: новый primary обязательно будет из тех, кто её получил.

**`j: true` — ждать, пока запись ляжет в журнал на диске.**\
Без этого запись может быть подтверждена, пока лежит только в памяти узлов.

---

### Read concern — что ты увидишь при чтении

**Read concern задаёт, какие данные считать видимыми для чтения.**\
Это особенно важно в replica set, где у узлов немного разные данные.

**`local` — последнее, что есть на узле.**\
Быстро, но можно прочитать запись, которая потом откатится.

**`majority` — только подтверждённое большинством.**\
Прочитанное уже не исчезнет при смене primary.

**`snapshot` — один момент времени для всех чтений транзакции.**\
Похоже на REPEATABLE READ в Postgres ([01-sql, раздел 4](01-sql.md#repeatable-read)).

---

### Значения по умолчанию

**Значения по умолчанию менялись между версиями.**\
Например, с MongoDB 5.0 write concern по умолчанию — `majority`, а раньше был `w: 1`.

> ⚠️ **Не полагайся на значения по умолчанию — задавай явно и проверяй.** Старый конфиг или чужой пример кода легко принесут `w: 1` «ради скорости».

---

## 8. Порядок без автоинкремента

**В Mongo нет `SERIAL` и `IDENTITY` — автоинкремента, как в Postgres.**\
Автоинкремент — колонка, в которую база сама подставляет следующий номер: 1, 2, 3…

**ObjectID упорядочен по времени, но только примерно.**\
Внутри — секунды и счётчик отдельного процесса ([раздел 1](#_id-и-objectid)). Между разными инстансами сервиса порядок внутри одной секунды не гарантирован.

**Время события тоже не уникально.**\
Два события вполне могут получить одинаковый `occurred_at`, особенно с точностью до миллисекунд.

**Для outbox, где порядок важен, нужен свой счётчик — и это создаёт горячую точку конкуренции.**\
Горячая точка — одно место, за которое борются все писатели: каждая транзакция хочет изменить один и тот же документ-счётчик.

> В задаче 04 ты столкнёшься с этим лично. Чем упорядочить и чем плох каждый вариант — 🤔 вопрос 4, цена под нагрузкой — 🎤 вопрос и ADR.

## 9. Индексы

**Шпаргалка раздела:**

| Индекс | Что делает |
|---|---|
| по одному полю | как обычный B-tree в SQL |
| составной | по нескольким полям; порядок полей важен |
| multikey | по массиву: каждый элемент получает запись в индексе |
| partial | только по документам, подходящим под условие |
| TTL | сам удаляет документы через заданное время |
| unique | запрещает повтор значения |
| covered query | запрос, которому хватает данных из индекса |

---

### Основное

**Без индекса Mongo читает всю коллекцию при каждом запросе.**\
В плане запроса это называется `COLLSCAN` — аналог `Seq Scan` в Postgres.

**Индексы в Mongo — тоже B-tree.**\
Всё из [01-sql, раздел 7](01-sql.md#7-индексы-и-explain) про сортировку, левый префикс и цену индекса на запись верно и здесь.

**Порядок полей в составном индексе подчиняется правилу ESR: Equality → Sort → Range.**\
Сначала поля, по которым ищут на равенство, потом поле сортировки, потом поле диапазона. Это та же телефонная книга из 01-sql, просто под другим именем.

---

### Особые виды индексов

#### Multikey

**Индекс по полю-массиву создаётся автоматически как multikey.**\
Каждый элемент массива получает свою запись в индексе, поэтому можно искать «документы, где в `tags` есть `"зима"`».

**Следи за размером.**\
Сто элементов в массиве у каждого из 10 миллионов документов — миллиард записей в индексе.

#### Partial

**Индекс только по документам, подходящим под условие (`partialFilterExpression`).**\
То же, что partial index в Postgres ([01-sql](01-sql.md#partial-index-частичный-индекс)): маленький индекс по нужной части коллекции.

**Mongo возьмёт такой индекс, только если из условия запроса следует условие индекса.**\
Если в запросе про это условие ничего не сказано, база не знает, не окажется ли ответ за пределами индекса.

#### TTL

**TTL-индекс (time to live) сам удаляет документы через заданное время после значения поля.**\
Удобно для сессий, временных токенов, логов.

**Фоновая чистка запускается раз в минуту.**\
Документ исчезнет не ровно в срок, а в пределах примерно минуты после него.

#### Covered query

**Если всё, что нужно запросу, есть в индексе, документы не читаются вообще.**\
Ответ собирается прямо из индекса. Аналог `Index Only Scan` в Postgres.

---

### Как проверить, что индекс работает

**`explain("executionStats")` показывает план — как `EXPLAIN ANALYZE` в Postgres.**\
Смотреть надо на три вещи:

- **`IXSCAN` или `COLLSCAN`** — сработал индекс или коллекция прочитана целиком;
- **`totalDocsExamined` против `nReturned`** — просмотрено сто тысяч, вернулось двадцать: индекс отбирает плохо;
- **стадия `SORT`** — сортировка в памяти, индекс не покрыл `sort`.

## 10. Шардирование

**Шпаргалка раздела:**

| Слово | Что значит |
|---|---|
| sharded cluster | коллекция разрезана между несколькими replica set |
| shard | один такой replica set со своей частью данных |
| mongos | роутер: клиент говорит с ним, он решает, на какой шард идти |
| config servers | хранят карту «какие данные на каком шарде» |
| shard key | поле, по которому решается, на какой шард положить документ |
| chunk | непрерывный диапазон значений shard key — единица переноса |
| balancer | фоновый процесс, который выравнивает данные между шардами |
| jumbo chunk | кусок, который нельзя разделить: в нём одно значение ключа |

---

### Как устроено

**Шардированный кластер разрезает коллекцию на части и раскладывает их по нескольким replica set.**\
Каждый такой replica set — шард; он хранит только свою часть данных.

**Клиент не знает про шарды: он подключается к mongos.**\
Mongos — роутер. Он смотрит в config servers, где лежит карта данных, и отправляет запрос на нужный шард.

**Данные внутри коллекции делятся на chunks — диапазоны значений shard key.**\
Balancer следит за равномерностью и переносит chunks с перегруженных шардов на свободные.

**Минимальный боевой кластер — около десятка серверов.**\
Три config servers, хотя бы два шарда по три реплики и пара mongos. Поэтому шардирование включают, только когда без него не обойтись.

---

### Shard key — самое важное решение

**Shard key — поле (или несколько полей), по которому Mongo решает, на какой шард положить документ.**\
От него зависит, ляжет ли нагрузка равномерно и сможет ли запрос пойти на один шард, а не на все.

**Хороший ключ:**

- **много разных значений** (высокая кардинальность): поле `status` с тремя значениями не разложит данные по десяти шардам;
- **равномерное распределение**: иначе один шард получит половину нагрузки;
- **есть в большинстве запросов**: иначе каждый запрос опрашивает все шарды (scatter-gather);
- **не растёт монотонно** или хешируется: иначе все новые записи идут в один шард.

**Монотонный ключ без хеширования — главная ошибка.**\
Если ключ — время или ObjectID, все новые документы больше всех старых и попадают в последний chunk на одном шарде. Этот шард «горит», остальные простаивают. Это называют **hot shard**.

**Два вида шардирования:**

- **ranged** — по диапазонам значений: хорошо для запросов по диапазону, плохо для монотонных ключей;
- **hashed** — по хешу значения: соседние значения расходятся по разным шардам, зато запрос по диапазону идёт на все шарды.

---

### Почему неудачный ключ не исправить дёшево

**Jumbo chunk — кусок, который перерос максимальный размер, но не делится.**\
Это бывает, когда в нём много документов с одним и тем же значением ключа: разрезать диапазон из одного значения нельзя.

**Сменить shard key можно (`reshardCollection`, с версии 5.0), но дорого.**\
База строит рядом вторую копию всей коллекции с новой раскладкой — нужен запас места и время, — а в конце ненадолго останавливает запись.

> **Вывод:** shard key выбирают один раз и очень внимательно, по реальным запросам и реальному распределению данных.

---

## 11. Change streams и aggregation pipeline

### Change streams

**Change stream — подписка на изменения в коллекции.**\
Приложение открывает поток и получает событие на каждую вставку, изменение и удаление.

**Под капотом change streams читают oplog.**\
Поэтому они тоже работают только на replica set или шардированном кластере.

**Это вариант CDC (change data capture) — «узнавать об изменениях, читая журнал базы».**\
CDC — альтернатива outbox для публикации событий, см. [09-patterns](09-patterns.md). Чем они отличаются и почему в этом курсе outbox — подумай, когда прочитаешь 09.

---

### Aggregation pipeline

**Aggregation pipeline — способ в Mongo делать то, что в SQL делают `GROUP BY`, подзапросы и `JOIN`.**\
Это список стадий: документы проходят их по очереди, каждая отдаёт следующей уже преобразованный поток.

**Основные стадии:**

| Стадия | Что делает | Аналог в SQL |
|---|---|---|
| `$match` | отбирает документы по условию | `WHERE` |
| `$project` | меняет форму документа: какие поля оставить, что посчитать | список полей в `SELECT` |
| `$group` | группирует и считает `$sum`, `$avg`, `$max` | `GROUP BY` |
| `$sort`, `$limit` | сортирует и обрезает | `ORDER BY`, `LIMIT` |
| `$unwind` | разворачивает массив: документ с тремя элементами → три документа | — |
| `$lookup` | подтягивает документы из другой коллекции | `JOIN`, но вложенным циклом |

**Порядок стадий — это и есть оптимизация.**\
`$match` ставят первым — только он умеет пользоваться индексом; `$lookup` — как можно позже, когда документов осталось мало.
