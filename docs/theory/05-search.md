# Поиск: OpenSearch / Elasticsearch

**Роль:** полнотекстовый поиск и фильтрация по множеству полей.
**Отвечает на вопрос:** как найти «клавиатура» по запросу «клавиатру» и отсортировать результаты по релевантности.

## Когда брать

- Пользователь ищет текстом, ошибается и ждёт, что поиск его поймёт: опечатки, морфология, синонимы.
- Нужна релевантность (BM25), а не просто «содержит подстроку».
- Нужен фасетный поиск: фильтры по десятку полей и счётчики «сколько товаров в каждой категории».
- Логи и observability (ELK, OpenSearch Dashboards) — отдельная огромная ниша.

## Когда не брать

- Как источник истины. Индекс — производная копия, которую должно быть можно пересобрать с нуля из базы или из лога событий.
- Поиск по точному ключу или простой префикс — это работа для B-tree индекса в базе.
- Объёмы маленькие, а требования скромные — сначала попробуй `tsvector` + `pg_trgm` в Postgres.

## OpenSearch vs Elasticsearch vs альтернативы

| | Elasticsearch | OpenSearch | Postgres FTS + pg_trgm | Meilisearch / Typesense |
|---|---|---|---|---|
| Происхождение | Elastic | форк ES 7.10 от AWS (2021) | встроено в Postgres | отдельные лёгкие движки |
| Лицензия | AGPL / SSPL / ELv2 (менялась) | Apache 2.0 | PostgreSQL | MIT / GPL |
| Масштаб | кластеры на петабайты | то же | один узел | средний |
| Операционная сложность | высокая | высокая | ноль (уже есть) | низкая |
| Релевантность и анализаторы | богато | богато | базово | хорошо из коробки |

## Что важно понимать

### Инвертированный индекс

Документ разбивается анализатором на токены (lowercase, стемминг, стоп-слова), и строится словарь «токен → список документов». Поэтому поиск по словам быстрый, а произвольный `LIKE '%ab%'` — нет. Поле `text` анализируется, поле `keyword` хранится как есть (для фильтров, сортировки, агрегаций). Маппинг полей задаётся явно: dynamic mapping угадывает типы по первому документу и часто ошибается.

### Near real-time

Записанный документ не виден поиску сразу — только после refresh (по умолчанию раз в секунду). В тестах ставят `refresh=true` на запись. В проде так не делают: каждый refresh создаёт сегмент.

### Нет транзакций с базой

Записать в Postgres и в OpenSearch атомарно нельзя. Поэтому индекс в этом репо наполняется **проектором** — потребителем событий из брокера. Он должен быть:

- **идемпотентным:** то же событие дважды → тот же результат;
- **устойчивым к порядку:** старое событие после нового не должно откатить документ. Здесь помогает external versioning: версия документа = версия агрегата, а OpenSearch сам отклоняет запись с меньшей версией.

### Переиндексация

Маппинг поля нельзя поменять на живом индексе. Создают новый индекс, наливают в него данные, переключают алиас. Подумай, откуда брать данные для наливки: из базы? Из лога событий в Kafka?

## 🔎 Изучи сам

- inverted index, analyzer, tokenizer, token filter
- BM25, TF-IDF
- `text` vs `keyword`, multi-fields
- fuzziness, edit distance (Левенштейн), n-grams, edge n-grams
- refresh, flush, segment merge, translog
- shards и replicas; почему число primary shards не меняют на лету
- index aliases, reindex, zero-downtime reindexing
- `version_type=external`, optimistic concurrency (`if_seq_no`/`if_primary_term`)
- aggregations, фасеты
- `tsvector`, `tsquery`, GIN-индекс, `pg_trgm`, similarity
- векторный поиск (kNN), гибридный поиск — куда это всё движется
