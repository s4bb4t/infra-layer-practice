## 1. Что такое реляционная база — коротко

**Шпаргалка раздела:**

| Слово | Что значит |
|---|---|
| таблица, строка, колонка | данные лежат таблицами; строка — одна запись, колонка — одно свойство с типом |
| схема | список таблиц, колонок и правил; база знает его заранее |
| primary key | колонка, по которой строка находится однозначно |
| constraint (ограничение) | правило, которое база проверяет при каждой записи |
| SQL | язык запросов: говоришь *что* нужно, база решает *как* |
| OLTP / OLAP | много мелких запросов / мало огромных |

---

### Таблицы и схема

**Реляционная база хранит данные в таблицах.**\
Это почти как лист Excel: сверху названия колонок, ниже — строки с данными.

**У таблицы фиксированный набор колонок, и у каждой колонки есть тип.**\
Тип говорит, что можно положить в колонку: текст, целое число, дату. Положить текст в числовую колонку база не даст.

**Строка таблицы — это одна запись.**\
В таблице заказов одна строка — один заказ со всеми его свойствами.

**Набор таблиц, колонок и правил называется схемой.**\
Схема — это «чертёж» данных: какие таблицы есть, что в них лежит и какие правила действуют.

**Схема фиксирована: база заранее знает, что у каждого заказа есть `customer_id`, и не сохранит заказ без него.**\
Это не неудобство, а смысл: база сама проверяет правила и не даёт записать мусор, даже если в коде баг.

---

### Наша таблица заказов

Вот она целиком, из `internal/infrastructure/postgres/migrations/00001_init.sql`:

```sql
CREATE TABLE orders (
    id          TEXT        PRIMARY KEY,                        -- уникальный, не NULL; по нему ищем заказ
    customer_id TEXT        NOT NULL,                           -- обязателен
    items       JSONB       NOT NULL,                           -- позиции заказа — JSON внутри колонки
    total_cents BIGINT      NOT NULL CHECK (total_cents >= 0),  -- база не даст записать отрицательную сумму
    status      TEXT        NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL,                           -- момент времени
    version     INTEGER     NOT NULL                            -- номер версии для optimistic locking (раздел 5)
);
```

Разберём, что здесь написано.

#### 1. `PRIMARY KEY` — первичный ключ

**Первичный ключ — колонка, которая однозначно определяет строку.**\
По значению `id` можно найти ровно один заказ, никогда не два.

**Он всегда уникален и никогда не бывает `NULL`.**\
`NULL` в SQL значит «значения нет». У первичного ключа значение есть всегда, и оно не повторяется.

**База автоматически строит по первичному ключу индекс.**\
Индекс — это «оглавление» для быстрого поиска (подробно в [разделе 7](#7-индексы-и-explain)). Поэтому `WHERE id = $1` работает быстро даже на миллиарде строк.

#### 2. Ограничения (constraints)

**Ограничение — правило, которое база проверяет при каждой записи.**\
Основные ограничения:

- `NOT NULL` — значение обязательно;
- `UNIQUE` — значение не повторяется в таблице;
- `CHECK (условие)` — значение должно удовлетворять условию, например `total_cents >= 0`;
- `FOREIGN KEY` — значение должно существовать в другой таблице.

**Если правило нарушено, запрос падает с ошибкой, и данные не меняются.**\
То есть плохие данные даже не попадут в таблицу: их отсечёт сама база.

#### 3. `FOREIGN KEY` — внешний ключ

**Внешний ключ значит: «значение в этой колонке обязано существовать в другой таблице».**\
Например, `order_items.order_id REFERENCES orders(id)`: позицию можно создать только для заказа, который действительно есть.

**Он работает в обе стороны.**\
Нельзя создать позицию для несуществующего заказа и нельзя удалить заказ, у которого остались позиции.

> У нас внешних ключей нет: позиции лежат прямо внутри колонки `items`. Хорошо это или плохо — вопрос шага 02.

#### 4. `JSONB` — JSON внутри колонки

**`JSONB` — колонка, в которой лежит JSON-документ.**\
Например, список позиций заказа: `[{"sku": "A1", "qty": 2, "price_cents": 500}]`.

**Postgres умеет искать по полям внутри этого JSON и строить по ним индексы.**\
Значит, это не просто «текст в колонке»: база понимает его структуру.

**Это способ хранить «полуструктурированные» данные, не уходя в документную базу.**\
Полуструктурированные — значит, у данных есть форма, но она может отличаться от записи к записи.

#### 5. `TIMESTAMPTZ` — момент времени

**`TIMESTAMPTZ` расшифровывается как «timestamp with time zone», но название обманчивое.**\
Часовой пояс в колонке не хранится.

**Postgres переводит время в UTC при записи и обратно в пояс сессии при чтении.**\
UTC — это «нулевой» часовой пояс, общий для всего мира. Сессия — текущее подключение к базе со своими настройками.

> Поэтому в нашем коде после чтения стоит `.UTC()`: так время всегда возвращается в одном и том же поясе, независимо от настроек подключения.

#### 6. `BIGINT` для денег

**Суммы хранятся в копейках целым числом.**\
1234 рубля 50 копеек лежат в базе как `123450`.

> Почему деньги — целое число копеек, а не дробное число рублей, — 🤔 вопрос 7 шага 01.

### SQL и планировщик

**SQL — язык запросов к реляционной базе.**\
Им создают таблицы, пишут данные и задают вопросы к данным.

**В SQL ты описываешь, что хочешь получить, а не как это сделать.**\
Например: «заказы клиента X, новые первыми, 20 штук». Как именно их найти, ты не пишешь.

**Как именно — решает планировщик (query planner) внутри базы.**\
Планировщик смотрит, какие есть индексы и сколько примерно строк в таблицах, и выбирает самый дешёвый способ выполнить запрос.

**Поэтому один и тот же запрос может работать быстро или медленно в зависимости от индексов.**\
Текст запроса в коде при этом не меняется: меняется только то, что база может использовать для его выполнения.

---

### OLTP и OLAP

**OLTP (Online Transaction Processing) — нагрузка «много маленьких запросов, каждый трогает несколько строк».**\
Создать заказ, оплатить заказ, показать заказ — каждый такой запрос работает с одной-двумя строками, но их тысячи в секунду.

**Postgres и MySQL — OLTP-базы.**\
Они созданы для того, чтобы быстро и надёжно выполнять именно такие мелкие операции.

**OLAP (Online Analytical Processing) — противоположность: «мало огромных запросов, каждый читает миллионы строк».**\
Например, «выручка по месяцам за 5 лет»: запрос один, но он проходит по всей истории.

> Для OLAP есть другие базы, см. [06-analytics](06-analytics.md). Почему — в [разделе 2](#2-когда-брать-когда-не-брать) ниже.

## 2. Когда брать, когда не брать

Реляционная база — не единственный вид хранилища, и у каждого вида своя сильная сторона. Поэтому до выбора сверь задачу с двумя списками ниже.

**Шпаргалка раздела:**

| Признак задачи | Что брать |
|---|---|
| ✅ связи между данными и правила, которые нельзя нарушать | реляционную базу |
| ✅ нужны транзакции «всё или ничего» | реляционную базу |
| ✅ вопросы к данным заранее неизвестны | реляционную базу |
| ✅ до нескольких терабайт данных | реляционную базу |
| ❌ сотни тысяч записей в секунду, и поток растёт | wide-column → [07](07-wide-column.md) |
| ❌ основной запрос — суммы и средние по миллиардам строк | колоночную базу → [06](06-analytics.md) |
| ❌ основной запрос — поиск по тексту с опечатками | поисковый движок → [05](05-search.md) |
| ❌ у каждой записи своя структура | документную базу → [02](02-documents.md), но сначала проверь `JSONB` |

---

### ✅ Когда брать

#### 1. Есть связи между сущностями и правила, которые нельзя нарушать

**Сущность** — это «вещь» из предметной области, о которой хранятся данные: заказ, клиент, товар.\
Связь значит, что одна сущность ссылается на другую: у заказа есть клиент, в заказе есть товары.

**Инвариант** — правило о данных, которое должно выполняться всегда:

- «email уникален»;
- «сумма не отрицательна»;
- «у позиции есть заказ».

Иначе говоря, это утверждение, которое верно в любой момент времени, а не «обычно» и не «если код не ошибся».

**Реляционная база проверяет такие правила сама, при каждой записи.**\
Запрос, который нарушил бы правило, просто падает с ошибкой, и плохие данные в таблицу не попадают.

**Защита работает, даже если в коде баг или в одну базу пишут два разных сервиса.**\
Проверку в коде можно забыть или написать с ошибкой, а мимо базы не пройдёт ни одна запись: это последний рубеж, общий для всех.

#### 2. Нужны транзакции

**«Списать с одного счёта и зачислить на другой» должно произойти целиком или не произойти вообще.**\
Если выполнится только первая половина, деньги исчезнут: с одного счёта ушли, на другой не пришли.

**Реляционная база даёт такую гарантию из коробки — это и есть транзакция.**\
Ты объединяешь несколько изменений в одну транзакцию, и база обещает, что даже после сбоя не останется «половинки».

> Подробно — в [разделе 3](#3-транзакции-и-acid).

#### 3. Запросы заранее неизвестны

**Через полгода продакт спросит: «сколько клиентов сделали больше трёх заказов в марте?»**\
Когда проектировали таблицы, такого вопроса никто не задавал, и это нормально: требования к продукту меняются постоянно.

**В SQL ответ — один новый запрос к уже лежащим данным.**\
Схему переделывать не нужно: пишешь запрос, база сама решает, как его выполнить, а таблицы и данные остаются как были.

```sql
SELECT customer_id
FROM orders
WHERE created_at >= '2026-03-01' AND created_at < '2026-04-01'
GROUP BY customer_id
HAVING count(*) > 3;
```

**Если новый запрос окажется медленным, обычно хватает добавить индекс.**\
Индекс — отдельная структура рядом с таблицей. Её можно построить в любой момент, ничего не меняя в самих данных ([раздел 7](#7-индексы-и-explain)).

**В key-value-хранилище данные пришлось бы заранее раскладывать под каждый вопрос.**\
Key-value-хранилище умеет одно: быстро отдать значение по ключу. Чтобы задать новый вопрос, нужно завести под него новый ключ и переложить под этот ключ все старые данные.

> Так же устроены Cassandra и DynamoDB. Подробно — в статье «Просто выберите Postgres» [в конце раздела](#почитать-к-этому-разделу-на-русском).

#### 4. Объём — от нуля до единиц терабайт на одном сервере

**Одна реляционная база на одном сервере спокойно хранит до нескольких терабайт.**\
Для масштаба: терабайт — это примерно миллиард заказов по килобайту каждый.

**Этого хватает подавляющему большинству продуктов.**\
Проще говоря, у большинства компаний данных гораздо меньше, чем кажется. Упереться в предел одного сервера — редкая проблема, а не обычная.

**Современный сервер с NVMe-дисками держит десятки тысяч транзакций в секунду.**\
NVMe — это SSD, подключённые к процессору напрямую через шину PCIe, а не через старый интерфейс SATA. Поэтому база успевает читать и писать на диск во много раз больше, чем на жёстких дисках.

> **Для сравнения:** миллион пользователей по 10 действий в день — это в среднем около **120 запросов в секунду**. В сотни раз меньше, чем держит один сервер.

### ❌ Когда не брать

#### 1. Нужна запись сотен тысяч событий в секунду с линейным ростом

**Речь о потоке, где каждую секунду приходят сотни тысяч новых записей:** клики, показания датчиков, логи.\
Это не заказы, которые создают люди, а события, которые генерируют машины, поэтому их бывает на порядки больше.

**«Линейный рост» значит: добавил второй сервер — можешь писать вдвое больше, добавил десятый — вдесятеро.**\
Именно этого хочется, когда поток событий растёт и растёт.

**Реляционная база в обычной конфигурации принимает все записи на один главный сервер.**\
Реплики ([раздел 12](#12-надёжность-и-масштабирование-wal-репликация)) могут разгрузить чтение, но писать в них нельзя: они только повторяют за главным то, что записано на нём.

**Главный сервер можно сделать мощнее, но не бесконечно.**\
У самого большого сервера, который можно купить, есть потолок. Когда поток записи его превысит, расти будет некуда.

> **Что брать:** wide-column-базу вроде Cassandra → [07](07-wide-column.md). Она с самого начала устроена как множество равноправных серверов, и каждый принимает свою часть записей.

#### 2. Основной запрос — агрегаты по миллиардам строк

**Агрегат** — одно число, посчитанное по множеству строк: сумма, среднее, количество.\
Например, чтобы получить «сумму продаж по регионам за год», нужно пройти по каждой продаже за год.

**Postgres хранит данные построчно: все колонки одной строки лежат на диске рядом.**\
Это удобно, когда нужен один заказ целиком: он читается с диска за один раз.

**Но для агрегата ему придётся прочитать все колонки всех строк, даже если для суммы нужны только две.**\
Если в таблице 50 колонок, а нужны 2, то 48 из каждых 50 прочитанных значений сразу выбрасываются. Почти вся работа диска уходит впустую.

```
Построчно (Postgres) — для SUM(amount) читается всё:
[ id=1 | region=msk | amount=1000 | status=paid | ... ещё 46 колонок ]
[ id=2 | region=spb | amount=2500 | status=new  | ... ещё 46 колонок ]

По колонкам (ClickHouse) — читаются только нужные:
region: [ msk, spb, ... ]
amount: [ 1000, 2500, ... ]
```

> **Что брать:** колоночную базу → [06](06-analytics.md). Она хранит каждую колонку отдельно, поднимает с диска в разы меньше данных и поэтому считает намного быстрее.

#### 3. Основной запрос — поиск по тексту с опечатками и сортировкой по релевантности

**Это поиск, как в интернет-магазине: «айфон чехол» должен найти «Чехол для iPhone 15».**\
Запрос и название товара написаны по-разному (другой порядок слов, другой язык, может быть опечатка), но человек ищет именно это.

**Релевантность** — насколько результат подходит под запрос.\
Сортировка по релевантности значит, что первыми показываются самые подходящие результаты, а не первые попавшиеся и не самые новые.

**В Postgres есть встроенный полнотекстовый поиск.**\
Он ищет по словам с учётом их форм («чехлы» найдёт «чехол»), и для простых случаев его хватает.

> **Что брать:** поисковый движок вроде Elasticsearch или OpenSearch → [05](05-search.md). Опечатки, синонимы и тонкая настройка ранжирования — их основная работа, и готовых инструментов для неё у них гораздо больше.

#### 4. У каждого документа своя форма, и схему нельзя зафиксировать

**Бывают данные без общей структуры:** анкеты, у каждой из которых свой набор полей, настройки разных интеграций.\
Такие записи называют **документами**, обычно это JSON-объекты.

**«Схему нельзя зафиксировать» значит, что колонки нельзя перечислить заранее.**\
У одной записи 5 полей, у соседней 30 совсем других, и таблица с фиксированным набором колонок на такие данные ложится плохо.

> **Что брать:** документную базу вроде MongoDB → [02](02-documents.md). Она хранит каждый документ целиком, как есть, и не требует, чтобы все документы были одинаковыми.

> ⚠️ **Но сначала проверь, не хватит ли колонки `JSONB` в Postgres — часто хватает.**\
> Общие поля держишь обычными колонками, а «разное» складываешь в одну `JSONB`-колонку, по которой тоже можно искать и строить индексы. У нас так хранятся позиции заказа (`items`).

## 3. Транзакции и ACID

**Шпаргалка раздела:**

| Буква | Гарантия | Одной фразой |
|---|---|---|
| **A** — Atomicity | атомарность | всё или ничего |
| **C** — Consistency | согласованность | правила не нарушаются |
| **I** — Isolation | изоляция | параллельные транзакции не мешают друг другу |
| **D** — Durability | долговечность | закоммичено = сохранено навсегда |

---

### Что такое транзакция

**Транзакция — группа операций, которую база выполняет как одно целое.**\
Либо применяются все операции группы, либо ни одна.

**Начинается с `BEGIN`, заканчивается `COMMIT` или `ROLLBACK`.**\
`COMMIT` — «зафиксировать всё, что сделано». `ROLLBACK` — «отменить всё, как будто ничего не было».

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'alice';
UPDATE accounts SET balance = balance + 100 WHERE id = 'bob';
COMMIT;
```

**Если между двумя `UPDATE` сервер упал, после перезапуска у Алисы будут те же деньги, что и до транзакции.**\
Незакоммиченная транзакция при восстановлении просто отменяется, и сто рублей не пропадают «в воздухе».

---

### ACID по буквам

Гарантии транзакций описывают аббревиатурой **ACID**. Разберём каждую букву.

#### A — Atomicity (атомарность)

**Транзакция применяется целиком или не применяется совсем.**\
«Атом» здесь значит «неделимое»: транзакцию нельзя выполнить наполовину.

> **Пример:** сервер упал между двумя `UPDATE` выше — откатятся оба.

#### C — Consistency (согласованность)

**После транзакции все ограничения выполняются.**\
Речь о `CHECK`, `UNIQUE`, `FOREIGN KEY` из [раздела 1](#2-ограничения-constraints): база не даст закоммитить транзакцию, которая их нарушает.

> **Пример:** `CHECK (balance >= 0)` не даст уйти в минус — упадёт вся транзакция, а не только один `UPDATE`.

#### I — Isolation (изоляция)

**Параллельные транзакции не должны мешать друг другу.**\
Точнее, изоляция определяет, насколько одна транзакция «видит» чужие незавершённые изменения.

> Это самая сложная буква, ей посвящён весь [раздел 4](#4-конкурентный-доступ-аномалии-и-уровни-изоляции).

#### D — Durability (долговечность)

**После `COMMIT` данные переживут падение сервера и выключение питания.**\
Если база ответила «закоммичено», значит, данные уже на диске, а не только в памяти.

> Как база это обеспечивает — в [разделе 12](#12-надёжность-и-масштабирование-wal-репликация) (WAL и `fsync`).

---

### Транзакции в нашем коде

**Use case не знает про `BEGIN` и `COMMIT`. Он знает только порт `TxManager`.**\
Порт — это интерфейс, который use case требует от внешнего мира. Как именно открывается транзакция, решает адаптер.

Сокращённо из `internal/app/usecase/orders.go`:

```go
err = uc.d.Tx.Do(ctx, func(ctx context.Context) error {
    if err := uc.d.Orders.Create(ctx, o); err != nil {
        return fmt.Errorf("create order: %w", err)
    }
    if err := uc.d.Outbox.Add(ctx, domain.NewOrderPlaced(uc.d.IDs.NewID(), o, now)); err != nil {
        return fmt.Errorf("add to outbox: %w", err)
    }
    return nil
})
```

**Функция вернула ошибку → `ROLLBACK`, вернула `nil` → `COMMIT`.**\
Use case просто возвращает ошибку, как обычно в Go, а адаптер превращает это в отмену или фиксацию.

**Адаптер `postgres.TxManager.Do` открывает транзакцию и кладёт её в `ctx`.**\
Дальше репозитории достают её оттуда функцией `conn(ctx, pool)` и выполняют свои запросы внутри этой транзакции.

**Если транзакции в `ctx` нет, запрос идёт в пул сам по себе.**\
Это называется **auto-commit**: каждый отдельный запрос — сам себе транзакция и коммитится сразу.

**Зачем всё это: заказ и событие о нём должны записаться вместе.**\
Иначе можно сохранить заказ и потерять событие, и никто из подписчиков не узнает о новом заказе.

> Подробно об этом — паттерн outbox в [09-patterns](09-patterns.md).

## 4. Конкурентный доступ: аномалии и уровни изоляции

**Шпаргалка раздела:**

| Аномалия | Что происходит |
|---|---|
| dirty read | прочитал чужие незакоммиченные данные |
| non-repeatable read | прочитал строку дважды — получил разное |
| phantom read | повторил запрос — появились новые строки |
| lost update | два «прочитал → посчитал → записал», одно изменение пропало |
| write skew | две транзакции проверили правило и вместе его нарушили |

| Postgres | MySQL (InnoDB) |
|---|---|
| по умолчанию READ COMMITTED | по умолчанию REPEATABLE READ |
| REPEATABLE READ = snapshot isolation | REPEATABLE READ + gap/next-key locks |
| SERIALIZABLE = SSI, нужны ретраи | SERIALIZABLE через блокировки |

---

### Проблема

**В базу одновременно ходят сотни запросов.**\
Каждый пользователь, каждый воркер, каждый инстанс сервиса — это свои запросы, и они идут параллельно.

**Если выполнять транзакции строго по очереди, всё будет корректно, но очень медленно.**\
Пока одна транзакция ждёт диск, остальные стояли бы в очереди без дела.

**Поэтому база выполняет их параллельно, и из-за этого возникают аномалии.**\
**Аномалия** — ситуация, когда результат параллельной работы отличается от того, что получилось бы при выполнении по очереди.

**Уровень изоляции — настройка, которая говорит базе, какие аномалии ты готов терпеть ради скорости.**\
Чем строже уровень, тем меньше аномалий, но тем больше база тратит на защиту, и тем чаще транзакциям приходится ждать или повторяться.

---

### Аномалии на примерах

Ниже две транзакции, T1 и T2, идут параллельно. Время течёт сверху вниз.

#### 1. Dirty read (грязное чтение)

**Читаешь данные, которые другая транзакция ещё не закоммитила и, возможно, откатит.**\
«Грязные» — потому что их ещё никто не подтвердил, и они могут исчезнуть.

| T1 | T2 |
|---|---|
| `UPDATE accounts SET balance = 0 WHERE id='alice'` | |
| | `SELECT balance … 'alice'` → **0** |
| `ROLLBACK` | |
| | работает с нулём, которого никогда не было |

#### 2. Non-repeatable read (неповторяемое чтение)

**В одной транзакции прочитал строку дважды и получил разные значения.**\
Между чтениями кто-то другой успел изменить строку и закоммитить.

| T1 | T2 |
|---|---|
| `SELECT balance … 'alice'` → 100 | |
| | `UPDATE … balance = 50 … 'alice'; COMMIT` |
| `SELECT balance … 'alice'` → **50** | |

#### 3. Phantom read (фантомное чтение)

**То же самое, но с набором строк: повторный запрос с тем же `WHERE` вернул новые строки.**\
Эти строки — «фантомы»: их не было при первом чтении, кто-то успел их вставить.

| T1 | T2 |
|---|---|
| `SELECT count(*) FROM orders WHERE customer_id='c1'` → 3 | |
| | `INSERT INTO orders (… 'c1' …); COMMIT` |
| `SELECT count(*) … 'c1'` → **4** | |

#### 4. Lost update (потерянное обновление)

**Две транзакции прочитали одно значение, обе посчитали новое и записали.**\
Вторая запись затирает первую, и изменение первой транзакции пропадает.

| T1 | T2 |
|---|---|
| `SELECT balance` → 100 | |
| | `SELECT balance` → 100 |
| в коде: 100 + 10 = 110 | |
| | в коде: 100 + 20 = 120 |
| `UPDATE … SET balance = 110; COMMIT` | |
| | `UPDATE … SET balance = 120; COMMIT` |
| | итог 120, а должно быть 130 |

**Обрати внимание на схему «прочитать → посчитать в Go → записать».**\
Если вместо этого написать `SET balance = balance + 10`, база сама прочитает актуальное значение под блокировкой, и аномалии не будет.

**Но часто логика не умещается в одно выражение SQL.**\
Например, домен проверяет, можно ли перевести заказ из `created` в `paid`, и эта проверка живёт в Go. Тогда нужна защита, см. [раздел 5](#5-блокировки-пессимистичные-и-оптимистичные).

#### 5. Write skew (перекос записи)

**Самая хитрая аномалия: две транзакции читают одни и те же данные, проверяют правило и пишут разные строки.**\
Каждая по отдельности правило не нарушает, а вместе нарушают.

**Пример: в больнице должен дежурить хотя бы один врач. Дежурят Алиса и Боб.**\
Оба одновременно решают уйти с дежурства, и каждый сначала проверяет, что остаётся кто-то ещё.

| T1 (Алиса уходит) | T2 (Боб уходит) |
|---|---|
| `SELECT count(*) WHERE on_call` → 2, значит можно | |
| | `SELECT count(*) WHERE on_call` → 2, значит можно |
| `UPDATE doctors SET on_call=false WHERE name='alice'` | |
| | `UPDATE doctors SET on_call=false WHERE name='bob'` |
| `COMMIT` | `COMMIT` → дежурных **0** |

**Транзакции меняли разные строки, поэтому блокировки строк не помогли.**\
Блокировка защищает строку от двух писателей сразу, а здесь каждый писал свою строку, и делить им было нечего.

---

### Уровни изоляции по стандарту

**Стандарт SQL описывает четыре уровня.**\
Чем ниже уровень, тем больше аномалий разрешено и тем быстрее работа.

| Уровень | Dirty read | Non-repeatable read | Phantom | Write skew и прочее |
|---|---|---|---|---|
| READ UNCOMMITTED | возможен | возможен | возможен | возможен |
| READ COMMITTED | — | возможен | возможен | возможен |
| REPEATABLE READ | — | — | по стандарту возможен | возможен |
| SERIALIZABLE | — | — | — | — |

**Стандарт описывает уровни через то, какие аномалии запрещены, а не через то, как это сделано.**\
Поэтому реальные базы ведут себя по-разному даже на уровне с одинаковым названием: каждая выполняет требования стандарта своим способом и часто строже, чем требуется.

> ⚠️ **Где lost update?** Его нет в таблице намеренно. Под этим именем имеют в виду две разные вещи:
> - **силами самой базы** — два `UPDATE … SET balance = balance + 10` одной строки, и один «потерялся». Этого не допускает ни один уровень, даже READ UNCOMMITTED: второй `UPDATE` ждёт блокировку строки ([раздел 5](#5-блокировки-пессимистичные-и-оптимистичные)). Поэтому в статье Рогова ([Куда копать дальше](#куда-копать-дальше)) написано, что потерянное обновление запрещено на всех уровнях;
> - **силами приложения** — как в примере выше: прочитали значение в Go, посчитали, записали константой (`SET balance = 120`). База получает два независимых запроса и не знает, что `120` вычислено из прочитанного ранее. На READ COMMITTED такое проходит без ошибок, и защищаться должен код: одним SQL-выражением, `FOR UPDATE` или проверкой версии.

---

### Как это устроено в Postgres

#### READ UNCOMMITTED

**В Postgres его не существует: если его попросить, получишь READ COMMITTED.**\
Грязного чтения в Postgres не бывает никогда, на любом уровне.

#### READ COMMITTED — по умолчанию

**Каждый запрос (не транзакция!) видит снимок данных на момент своего начала.**\
Снимок — это «фотография» всех закоммиченных данных. Каждый новый запрос делает новую фотографию.

**Поэтому два `SELECT` в одной транзакции могут увидеть разное.**\
Между ними могла закоммититься любая другая транзакция, и второй `SELECT` её уже увидит.

**Отсюда главное практическое правило: не принимай решение по данным, прочитанным предыдущим запросом.**\
К моменту следующего запроса эти данные могли устареть. Рогов называет это **несогласованным чтением** и подробно разбирает на примере со счетами.

#### REPEATABLE READ

**На деле это snapshot isolation (изоляция снимком).**\
Вся транзакция видит один снимок — тот, что был на момент её первого запроса.

**Чужие коммиты после этого не видны, фантомов тоже нет.**\
Сколько бы раз ты ни повторил запрос, увидишь те же данные.

**Если меняешь строку, которую после твоего снимка изменил кто-то другой, транзакция падает.**\
Postgres не затрёт чужое изменение, а вернёт ошибку `could not serialize access due to concurrent update`.

#### SERIALIZABLE

**Реализован как SSI (serializable snapshot isolation).**\
Это snapshot isolation плюс слежка за тем, кто какие данные читал.

**Если параллельные транзакции могли дать результат, невозможный при выполнении по очереди, одну из них база роняет.**\
Как в примере с врачами: одна из двух транзакций получит ошибку `40001 serialization_failure`.

> ⚠️ **На REPEATABLE READ и SERIALIZABLE ошибка сериализации — нормальная работа, а не баг.**\
> Код обязан её поймать и **повторить транзакцию целиком**, с первого чтения. Если ретраев нет, высокий уровень изоляции просто превращает аномалию в ошибку 500.

---

### Как это устроено в MySQL (InnoDB)

**InnoDB — движок хранения, который MySQL использует по умолчанию.**\
Движок — это часть MySQL, которая отвечает за то, как данные лежат на диске и как работают транзакции. «MySQL» в этом файле означает MySQL с InnoDB.

**По умолчанию уровень REPEATABLE READ, а не READ COMMITTED.**\
То есть в MySQL «из коробки» изоляция строже, чем в Postgres.

**Обычный `SELECT` читает из снимка транзакции. Это называют consistent read.**\
Как в Postgres на REPEATABLE READ: вся транзакция видит одни и те же данные.

**Но `UPDATE`, `DELETE` и `SELECT … FOR UPDATE` читают последнюю закоммиченную версию строки, а не снимок. Это называют locking read.**\
Значит, в одной транзакции `SELECT` может показать одно, а `UPDATE … WHERE` увидит другое. Это частый источник сюрпризов.

**Чтобы при locking read не было фантомов, InnoDB блокирует не только найденные строки, но и промежутки между ними.**\
Это **gap lock** (блокировка промежутка) и **next-key lock** (блокировка строки вместе с промежутком перед ней).

> **Пример:** `SELECT … WHERE customer_id = 'c1' FOR UPDATE` может запретить другим вставлять новые заказы для `c1`, хотя этих строк ещё не существует. Из-за этого в MySQL чаще случаются неожиданные ожидания и deadlock'и ([раздел 5](#5-блокировки-пессимистичные-и-оптимистичные)).

---

### Как задать уровень

**В SQL уровень задаётся на транзакцию.**\
По умолчанию используется уровень из настроек сервера, но для отдельной транзакции его можно поменять.

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;             -- Postgres, на одну транзакцию
SET TRANSACTION ISOLATION LEVEL READ COMMITTED; -- MySQL, перед следующей транзакцией
```

**В Go уровень передаётся при открытии транзакции.**\
В pgx: `pool.BeginTx(ctx, pgx.TxOptions{IsoLevel: pgx.Serializable})`. В `database/sql`: `db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelSerializable})`.

## 5. Блокировки: пессимистичные и оптимистичные

**Шпаргалка раздела:**

| Инструмент | Что делает |
|---|---|
| row lock | `UPDATE`/`DELETE` блокирует строку до конца транзакции |
| `SELECT … FOR UPDATE` | прочитать и сразу заблокировать |
| `NOWAIT` | не ждать блокировку, сразу ошибка |
| `SKIP LOCKED` | пропустить заблокированные строки |
| колонка `version` | оптимистичная блокировка: проверка в момент записи |
| advisory lock | блокировка на произвольное число |

**Уровень изоляции — не единственный способ защититься от аномалий.**\
Часто проще и дешевле защитить конкретное место явно: заблокировать нужную строку или проверить её версию.

---

### Как UPDATE ведёт себя при конкуренции

> Это база для обоих подходов ниже, разберись в ней хорошо.

#### 1. Любой `UPDATE` или `DELETE` берёт блокировку строки (row lock)

**Блокировка ставится на каждую строку, которую запрос меняет.**\
Пока она стоит, никто другой эту строку изменить не может.

**Блокировка держится до конца транзакции, а не до конца запроса.**\
Даже если `UPDATE` выполнился за миллисекунду, строка остаётся заблокированной до `COMMIT` или `ROLLBACK`.

#### 2. Второй писатель ждёт

**Если второй `UPDATE` хочет изменить ту же строку, он ждёт, пока первая транзакция закончится.**\
Он не падает и не перезаписывает, а просто стоит в очереди за блокировкой.

#### 3. После ожидания — перепроверка

**Что происходит, когда ожидание кончилось, зависит от базы и уровня изоляции.**\
У разных баз и уровней здесь разное поведение, поэтому его стоит знать точно.

**В Postgres на READ COMMITTED второй `UPDATE` перечитывает свежую версию строки и заново проверяет свой `WHERE`.**\
Если строка больше не подходит под условие, она не обновляется.

---

### Пример на счетах

Списание только при достаточном балансе:

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 'alice' AND balance >= 100;
```

**Баланс Алисы 150. Две транзакции одновременно пытаются списать по 100.**\
Вместе они хотят 200, а есть только 150, значит одна из них должна получить отказ.

1. T1 берёт блокировку строки, баланс становится 50, T1 коммитит.
2. T2 ждала блокировку. Дождалась, перечитала строку и увидела баланс 50.
3. Условие `balance >= 100` больше не выполняется, поэтому обновилось **0 строк**.
4. Код видит `RowsAffected() == 0` и понимает, что денег не хватило.

**Ушёл в минус? Нет. Потерялось обновление? Нет.**\
И для этого не понадобились ни SERIALIZABLE, ни явные блокировки: хватило одного `UPDATE` с правильным `WHERE`.

---

### Пессимистичная блокировка: `SELECT … FOR UPDATE`

**«Пессимистичная» — потому что исходит из того, что конфликт будет, и заранее его предотвращает.**\
Сначала блокируешь строку, потом спокойно работаешь с ней.

```sql
BEGIN;
SELECT * FROM orders WHERE id = $1 FOR UPDATE;  -- взяли блокировку строки, другие ждут
-- ... в Go проверили бизнес-правила, посчитали новое состояние ...
UPDATE orders SET status = 'paid' WHERE id = $1;
COMMIT;                                          -- отпустили блокировку
```

**`FOR UPDATE` значит «прочитай и сразу заблокируй, как будто я уже меняю эту строку».**\
Пока транзакция не закончилась, никто другой не сможет изменить строку или тоже взять её `FOR UPDATE`: они будут ждать.

#### Модификаторы

**`NOWAIT` — не ждать.**\
Если строка уже заблокирована, сразу вернуть ошибку, а не стоять в очереди.

**`SKIP LOCKED` — не ждать и не падать.**\
Заблокированные строки молча пропускаются, и запрос возвращает только свободные.

> **Классический пример:** очередь задач в таблице. Несколько воркеров делают `SELECT … WHERE status='new' LIMIT 10 FOR UPDATE SKIP LOCKED`, и каждый получает свою пачку.\
> Подумай, где у нас такое есть и что было бы без `SKIP LOCKED` — это вопрос шага 02.

#### Минусы

**Блокировка держится всю транзакцию.**\
Если внутри транзакции медленный код или, хуже, сетевой вызов (HTTP в платёжку), все остальные ждут его.

**Под высокой конкуренцией запросы выстраиваются в очередь.**\
Чем больше желающих изменить одну строку, тем длиннее очередь и тем медленнее каждый запрос.

**Можно получить deadlock.**\
Об этом ниже.

---

### Оптимистичная блокировка: колонка `version`

**«Оптимистичная» — потому что исходит из того, что конфликта скорее не будет.**\
Ничего заранее не блокирует, а в момент записи проверяет, не изменил ли кто-то строку.

**У строки есть номер версии.**\
Читаешь строку и запоминаешь версию. Когда пишешь, ставишь условие «только если версия всё ещё та, что я прочитал», и увеличиваешь её на один.

```sql
UPDATE t SET ..., version = version + 1 WHERE id = $1 AND version = $2;
```

**Обновилась 1 строка — успех. Обновилось 0 — либо строки нет, либо кто-то успел изменить её раньше.**\
Во втором случае возвращаем `ErrConflict`. Вызывающий перечитывает строку и решает, повторять ли.

> У нас так устроен `Orders.Update`, а контракт-тест «concurrent updates of one version: exactly one wins» это проверяет.\
> **Почему этого хватает на READ COMMITTED**, без SERIALIZABLE и без `FOR UPDATE`, — вопрос шага 02. Ответ складывается из подраздела [«Как UPDATE ведёт себя при конкуренции»](#как-update-ведёт-себя-при-конкуренции) выше.

#### Сравнение

| | Пессимистичная | Оптимистичная |
|---|---|---|
| Когда проверяется конфликт | до изменения (ждём блокировку) | в момент записи (сравниваем версию) |
| Что видит проигравший | ждёт, потом работает со свежими данными | получает ошибку конфликта и решает сам |
| Хорошо, когда | конфликты частые, транзакции короткие | конфликты редкие; между чтением и записью может пройти время (даже минуты: форма редактирования в браузере) |
| Плохо, когда | долгие транзакции, сетевые вызовы внутри | конфликты частые: много работы уходит в ретраи |

---

### Deadlock (взаимная блокировка)

**Две транзакции ждут друг друга и поэтому никогда не дождутся.**\
Каждая держит строку, которая нужна другой.

| T1 | T2 |
|---|---|
| блокирует строку A | |
| | блокирует строку B |
| хочет B — ждёт T2 | |
| | хочет A — ждёт T1 |

**База это замечает и убивает одну из транзакций.**\
Postgres проверяет это раз в `deadlock_timeout` (по умолчанию раз в секунду) и возвращает ошибку `40P01 deadlock_detected`; MySQL — ошибку `1213`. Вторая транзакция продолжает работу.

#### Как избегать

- **Блокировать строки в одном и том же порядке** во всём коде, например всегда по возрастанию `id`. Тогда две транзакции не смогут взять строки «крест-накрест».
- **Держать транзакции короткими.** Чем меньше транзакция держит блокировки, тем меньше шанс столкнуться.
- **Быть готовым повторить транзакцию**, которую база убила.

#### Как разбираться

**При deadlock база пишет, какие запросы в нём участвовали.**\
В Postgres — в лог сервера. В MySQL — в вывод `SHOW ENGINE INNODB STATUS`, секция `LATEST DETECTED DEADLOCK`.

---

### Advisory locks

**Postgres умеет блокировать не строку, а произвольное число: `SELECT pg_advisory_lock(42)`.**\
Сама база этому числу никакого смысла не придаёт.

**Смысл придумываешь ты.**\
Например, «42 — это блокировка на применение миграций» или «hash(customer_id) — блокировка на пересчёт бонусов клиента».

**Так несколько процессов договариваются через базу.**\
Им не нужны отдельные таблицы для блокировок: достаточно договориться, какое число что означает.

---

## 6. MVCC: как база показывает разным транзакциям разное

**Шпаргалка раздела:**

| | Postgres | MySQL (InnoDB) |
|---|---|---|
| где старые версии строк | прямо в таблице | в undo log |
| кто убирает | VACUUM / autovacuum | фоновый поток purge |
| что раздувается | таблицы и индексы (bloat) | undo log (history list length) |
| общий враг | долгие транзакции | долгие транзакции |

---

### Как такое возможно

**Из раздела 4 следует странное: две транзакции в один момент видят разные значения одной строки.**\
Одна видит баланс 100, другая — 50, и обе правы.

**Ответ: строка не одна.**\
База хранит **несколько версий** каждой строки и каждой транзакции показывает ту, которая подходит под её снимок.

**Это называется MVCC (Multi-Version Concurrency Control).**\
По-русски — многоверсионное управление конкурентным доступом.

**Главное следствие: читатели не блокируют писателей, а писатели не блокируют читателей.**\
Пока T1 меняет строку, T2 спокойно читает её старую версию и ничего не ждёт. Ждать друг друга приходится только двум писателям одной строки.

> Postgres и MySQL реализуют MVCC по-разному, и от этого зависит, как их обслуживать.

---

### Postgres: версии лежат прямо в таблице

**`UPDATE` в Postgres не меняет строку на месте.**\
Он записывает рядом новую копию строки (её называют **tuple**), а старую помечает «устаревшей, начиная с транзакции N».

**`DELETE` тоже ничего не стирает, а только помечает.**\
Строка физически остаётся в таблице, просто новые транзакции её больше не видят.

**Старые версии называют dead tuples, «мёртвые строки».**\
Они остаются в таблице и занимают место, пока могут понадобиться какой-то ещё работающей транзакции.

**Убирает их процесс VACUUM.**\
Он находит версии, которые больше никому не видны, и помечает их место как свободное для новых записей. Обычно VACUUM запускается сам — это **autovacuum**.

**Если мёртвых строк копится больше, чем VACUUM успевает убирать, таблица и индексы раздуваются.**\
Это называется **bloat**: данных 1 ГБ, а файл занимает 10 ГБ. Запросы замедляются, потому что читают с диска больше страниц.

> ⚠️ **Долгая транзакция — враг VACUUM.** Если транзакция открыта час (забыли закрыть, долгий отчёт), VACUUM не имеет права удалить ни одну версию новее её начала: вдруг ей понадобится. За этот час bloat растёт во **всех** таблицах.

---

### MySQL InnoDB: версии лежат в undo log

**`UPDATE` меняет строку на месте, а старое значение записывает в отдельную область — undo log.**\
Undo log — «журнал отмены». Если транзакции нужна старая версия строки, InnoDB восстанавливает её оттуда.

**Отдельного VACUUM не нужно: старые записи undo чистит фоновый поток purge.**\
Purge работает сам, вручную его запускать не надо.

**Но проблема долгих транзакций та же.**\
Пока открыта старая транзакция, purge не может чистить undo, и он растёт. За этим следят по метрике **history list length**.

---

### Что из этого вынести в код

**Не держи транзакцию открытой дольше, чем нужно.**\
Никаких сетевых вызовов, `time.Sleep` или ожидания пользователя внутри `TxManager.Do`.

**В Postgres частый `UPDATE` одной и той же строки порождает много мёртвых версий.**\
Например, счётчик просмотров на каждый запрос. Это нормально, если autovacuum настроен, но знать об этом нужно.

---

## 7. Индексы и EXPLAIN

**Шпаргалка раздела:**

| Слово | Что значит |
|---|---|
| Seq Scan | база читает всю таблицу подряд |
| индекс | отдельная структура для быстрого поиска |
| B-tree | индекс по умолчанию, отсортированное дерево |
| составной индекс | индекс по нескольким колонкам; работает по левому префиксу |
| partial index | индекс только по части строк |
| `EXPLAIN ANALYZE` | выполнить запрос и показать, как база его выполнила |

---

### Зачем индекс

**Без индекса, чтобы найти заказы клиента, базе нужно прочитать всю таблицу строку за строкой.**\
Это называется **Seq Scan** (sequential scan, последовательное сканирование): каждую строку достают и проверяют условие.

**На 100 строках это мгновенно, на 100 миллионах — секунды или минуты.**\
Время растёт вместе с размером таблицы, даже если нужны всего три строки.

**Индекс — отдельная структура рядом с таблицей, которая позволяет найти нужные строки, не читая всё подряд.**\
Как алфавитный указатель в конце книги: чтобы найти «MVCC», не листаешь 500 страниц, а смотришь указатель, видишь «стр. 237» и сразу открываешь её.

---

### B-tree — индекс по умолчанию

**`CREATE INDEX ... ON t (col)` без уточнений создаёт B-tree — сбалансированное дерево.**\
«Сбалансированное» значит, что путь от корня до любого значения одной длины, поэтому любой поиск занимает одинаковое время.

**Он хранит значения колонки в отсортированном порядке, и для каждого значения — ссылку на строку в таблице.**\
Сортировка — ключ ко всему остальному: именно из-за неё B-tree умеет так много.

**Поиск по нему занимает логарифмическое время.**\
На миллиарде строк это около 4–5 переходов по дереву, то есть несколько чтений с диска вместо миллиарда.

**Поскольку значения отсортированы, B-tree помогает не только с `=`.**\
Он ускоряет:

- `<`, `>`, `BETWEEN` — диапазоны;
- `ORDER BY` — данные уже лежат по порядку;
- `LIKE 'abc%'` — поиск по началу строки.

**Не помогает с `LIKE '%abc%'`.**\
Если искомый кусок в середине, сортировка по началу строки бесполезна.

**Индекс можно читать в обе стороны, но порядок колонок внутри составного индекса важен.**\
Об этом — сразу ниже.

---

### Составной индекс и правило левого префикса

**Индекс может быть по нескольким колонкам: `CREATE INDEX ON people (last_name, first_name)`.**\
Такой индекс называют составным.

**Он отсортирован сначала по первой колонке, а внутри одинаковых значений первой — по второй.**\
Точно как телефонная книга: сначала по фамилии, внутри одной фамилии — по имени.

```
Иванов  Алексей
Иванов  Борис
Иванов  Пётр
Петров  Алексей
Петров  Иван
Сидоров Борис
```

**Что такая книга умеет быстро:**

| Запрос | Быстро? | Почему |
|---|---|---|
| `WHERE last_name = 'Иванов'` | ✅ | все Ивановы идут подряд |
| `WHERE last_name = 'Иванов' AND first_name = 'Борис'` | ✅ | нашли Ивановых, внутри них Бориса |
| `WHERE last_name = 'Иванов' ORDER BY first_name` | ✅ | внутри Ивановых имена уже упорядочены — **сортировать не нужно**; с `LIMIT 1` база прочитает ровно одну запись |
| `WHERE first_name = 'Борис'` | ❌ | Борисы разбросаны по всей книге, придётся листать её целиком |

**Это и есть правило левого префикса.**\
Составной индекс помогает, только если условие задаёт его колонки слева направо без пропусков.

**Обычно сначала ставят колонки, по которым ищут на равенство, потом ту, по которой сортируют или задают диапазон.**\
Так база сначала сужает поиск до одного «раздела книги», а внутри него данные уже лежат в нужном порядке.

> В шаге 02 ты сам выберешь индекс под `ListByCustomer` и сравнишь планы. Примерь его на телефонную книгу.

---

### Partial index (частичный индекс)

**Индекс можно построить не по всей таблице, а только по строкам, подходящим под условие.**\
Пример из нашей миграции:

```sql
CREATE INDEX outbox_unpublished ON outbox (seq) WHERE published_at IS NULL;
```

**В outbox через месяц работы миллионы опубликованных событий и единицы неопубликованных.**\
Relay — процесс, который публикует события, — ищет только неопубликованные.

**Индекс по всей таблице был бы огромным, а этот содержит только неопубликованные строки и поэтому крошечный.**\
Как только событие помечается опубликованным, оно само выпадает из индекса.

---

### Сколько стоит индекс

**Индекс не бесплатный: каждый `INSERT` пишет и в таблицу, и в каждый её индекс.**\
Пять индексов — примерно шесть записей вместо одной. Это называют **write amplification** (усиление записи).

**`UPDATE` колонки, входящей в индекс, тоже обновляет индекс.**\
Чем больше индексов затрагивает изменение, тем дороже каждая запись.

**Индексы занимают место на диске и в памяти.**\
Если индексы не влезают в оперативную память, базе приходится читать их с диска, и всё становится медленнее.

> **Вывод:** индекс заводят под **конкретный частый запрос**, а не «на всякий случай на каждую колонку».

---

### Другие типы индексов в Postgres

**Кроме B-tree, есть специальные индексы под особые виды поиска.**\
Сейчас достаточно знать, что они существуют и для чего.

| Тип | Для чего |
|---|---|
| **GIN** | «содержит ли»: поля внутри `JSONB`, элементы массива, слова в полнотекстовом поиске, `ILIKE '%abc%'` через расширение `pg_trgm` |
| **GiST** | геометрия и геоданные (PostGIS), диапазоны, «ближайший сосед» |
| **BRIN** | огромные таблицы, где данные физически лежат по порядку (логи по времени): очень маленький, но грубый |
| **Hash** | только `=`; на практике почти всегда хватает B-tree |

**В MySQL почти все индексы — B-tree.**\
Плюс есть **FULLTEXT** для поиска по тексту и пространственные индексы для геоданных.

---

### EXPLAIN и EXPLAIN ANALYZE

**Единственный честный способ узнать, использует ли запрос индекс, — спросить у базы.**\
Догадки «наверное, индекс подхватится» часто неверны: решение принимает планировщик.

**`EXPLAIN <запрос>` показывает план: как база собирается выполнять запрос.**\
Сам запрос при этом не выполняется.

**`EXPLAIN ANALYZE <запрос>` выполняет запрос и показывает план вместе с реальным временем и числом строк на каждом шаге.**\
Так видно не только что база планировала, но и что произошло на самом деле.

> ⚠️ `EXPLAIN ANALYZE UPDATE …` и `EXPLAIN ANALYZE DELETE …` **действительно изменят данные**. Оборачивай в `BEGIN; … ROLLBACK;`.

#### Как читать план

Пример на условной таблице `users` с индексом по `email`:

```
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'a@b.c';

Index Scan using users_email_idx on users  (cost=0.42..8.44 rows=1 width=72) (actual time=0.031..0.032 rows=1 loops=1)
  Index Cond: (email = 'a@b.c'::text)
Planning Time: 0.110 ms
Execution Time: 0.050 ms
```

| Что в плане | Что значит |
|---|---|
| строки плана | **узлы**; читай изнутри наружу: самый вложенный выполняется первым и отдаёт строки родителю |
| `cost=0.42..8.44` | **оценка** планировщика в условных единицах: до первой строки и до последней. Не миллисекунды — нужна, чтобы сравнивать планы |
| `rows=1` в первых скобках | сколько строк планировщик **ожидал** |
| `rows=1` в `actual` | сколько получилось **на самом деле**. Расходятся в сотни раз — значит, у планировщика устаревшая статистика |
| `actual time=0.031..0.032` | реальные миллисекунды до первой и до последней строки |
| `loops` | сколько раз выполнялся узел; время и строки указаны **на один проход** |

#### Узлы, которые встречаются чаще всего

| Узел | Что значит |
|---|---|
| `Seq Scan` | прочитал всю таблицу |
| `Index Scan` | нашёл в индексе, за каждой строкой сходил в таблицу |
| `Index Only Scan` | всё нужное было в самом индексе, в таблицу не ходил |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | собрал по индексу список страниц, потом прочитал их пачкой: компромисс, когда строк много |
| `Sort` | сортировал сам. Если стоит над `Seq Scan`, значит индекс под `ORDER BY` не помог |
| `Limit` | остановился, набрав N строк |

#### Подводные камни при проверке плана

**На маленькой таблице планировщик часто выбирает `Seq Scan` даже при наличии индекса — и правильно делает.**\
Прочитать 3 страницы подряд дешевле, чем ходить по дереву. Проверяй на реалистичном объёме: в шаге 02 это 100 тысяч строк.

**После массовой вставки обнови статистику: `ANALYZE orders;`.**\
Иначе планировщик думает, что таблица всё ещё пустая, и строит план под пустую таблицу. Autovacuum сделает это сам, но не мгновенно.

**`EXPLAIN (ANALYZE, BUFFERS)` дополнительно показывает, сколько страниц прочитано из кэша и сколько с диска.**\
Это помогает понять, медленный ли запрос сам по себе или ему просто не повезло с холодным кэшем.

## 8. Пул соединений

**Шпаргалка раздела:**

| | Postgres + `pgxpool` | MySQL + `database/sql` |
|---|---|---|
| одно соединение на сервере | отдельный процесс ОС | отдельный поток |
| лимит соединений базы по умолчанию | `max_connections = 100` | `max_connections = 151` |
| максимум в пуле по умолчанию | `max(4, число CPU)` | **без ограничения** (`MaxOpenConns = 0`) |

---

### Почему соединение дорогое

**Соединение с Postgres — это отдельный процесс операционной системы на сервере базы.**\
На каждое новое соединение Postgres делает `fork` (запускает копию себя), и этот процесс занимает несколько мегабайт памяти.

**Открыть соединение — долго.**\
Это TCP-рукопожатие, TLS-шифрование, проверка пароля и запуск процесса: миллисекунды, а не микросекунды.

**MySQL использует потоки, а не процессы, поэтому соединение у него дешевле, но тоже не бесплатное.**\
Поток легче процесса, но память и время на установку соединения всё равно тратятся.

**Поэтому соединения не открывают на каждый запрос, а держат открытыми и переиспользуют.**\
Набор таких заранее открытых соединений называется **пулом** (connection pool).

**У базы есть лимит соединений — `max_connections`.**\
По умолчанию это 100 в Postgres и 151 в MySQL. Десять инстансов сервиса по 20 соединений — уже 200, больше лимита.

---

### Пул в Go

**Тысяча горутин ≠ тысяча соединений.**\
Горутина берёт соединение из пула, делает запрос и возвращает его. Если свободных соединений нет, горутина ждёт, пока какое-то освободится.

#### `pgxpool` — у нас для Postgres

**По умолчанию максимум соединений — `max(4, число CPU)`.**\
На 8-ядерной машине это 8 соединений.

**Меняется через `pool_max_conns` в строке подключения или `pgxpool.Config.MaxConns`.**\
Строка подключения — это URL вида `postgres://user:pass@host/db?pool_max_conns=20`.

#### `database/sql` — у нас для MySQL

**По умолчанию `MaxOpenConns = 0`, то есть без ограничения.**\
Под нагрузкой сервис может открыть столько соединений, что упрётся в `max_connections` базы, и новые подключения начнут падать.

**Поэтому его обычно ограничивают явно.**\
Для этого есть `db.SetMaxOpenConns(…)`, `SetMaxIdleConns(…)` (сколько держать свободных) и `SetConnMaxLifetime(…)` (через сколько пересоздавать соединение).

> **Ограниченный пул — это хорошо.** Он ограничивает, сколько параллельной работы сервис отправит в базу. Базе с 8 ядрами 500 одновременных запросов не помогут: они будут толкаться за процессор и диск, и все станут медленнее.

---

### Что держит соединение занятым дольше, чем кажется

#### 1. Открытая транзакция

**Соединение не вернётся в пул, пока транзакция не закончится.**\
Вся транзакция идёт по одному соединению, и пока она открыта, им не может пользоваться никто другой.

#### 2. Незакрытые `rows`

**Пока не вызван `rows.Close()` и не прочитаны все строки, соединение занято.**\
Забыл закрыть — соединение «утекло». Через какое-то время утекут все, и горутины встанут в ожидании.

**Линтер `sqlclosecheck` ловит это для `database/sql`.**\
Он проверяет, что после `Query` где-то есть `rows.Close()`.

> ⚠️ **После цикла по `rows` обязательно проверяй `rows.Err()`.** Ошибка посреди чтения (например, оборвалась сеть) не вернётся из `rows.Next()` — она проявится только там.

---

### PgBouncer

**Когда инстансов сервиса много, перед Postgres ставят PgBouncer — отдельный лёгкий прокси-пул.**\
Прокси — это программа-посредник: сервисы подключаются к ней, а она уже к базе.

**Сервисы открывают сотни соединений к PgBouncer, а он держит к Postgres всего несколько десятков настоящих.**\
Так база не тратит память на сотни процессов, а сервисы не замечают разницы.

**Режимы PgBouncer — это ответ на вопрос «когда настоящее соединение отдаётся другому клиенту».**\
Чем раньше отдаётся, тем больше экономия, но тем больше ограничений.

| Режим | Соединение отдаётся другому | Цена |
|---|---|---|
| **session** | когда клиент отключился | экономии почти нет |
| **transaction** | после каждой транзакции | самый популярный; но всё, что живёт дольше транзакции (настройки `SET`, **prepared statements**, advisory locks на сессию, `LISTEN`), может «уехать» к другому клиенту |
| **statement** | после каждого запроса | транзакции из нескольких запросов невозможны |

#### Prepared statements и transaction-режим

**Prepared statement (подготовленный запрос) — запрос, который база один раз разобрала и спланировала.**\
Она сохраняет его под именем **на этом соединении**, а потом выполняет по имени с разными параметрами. pgx делает так автоматически.

**В transaction-режиме PgBouncer следующий запрос может попасть на другое настоящее соединение.**\
Там такого имени нет, и запрос падает с ошибкой.

> **Как лечится:** настройкой pgx (`default_query_exec_mode`) или новыми версиями PgBouncer (1.21+), которые научились отслеживать prepared statements сами.

## 9. Миграции

**Шпаргалка раздела:**

| Слово | Что значит |
|---|---|
| миграция | файл с изменением схемы, у каждого свой номер |
| goose | наш инструмент миграций |
| `-- +goose Up` / `Down` | как применить / как откатить |
| `ACCESS EXCLUSIVE` | самая сильная блокировка таблицы: ждут все, даже `SELECT` |
| `CREATE INDEX CONCURRENTLY` | построить индекс, не блокируя запись |
| expand / contract | менять схему в несколько совместимых шагов |

---

### Что такое миграция

**Миграция — файл с изменением схемы: создать таблицу, добавить колонку, построить индекс.**\
Каждый файл описывает один шаг от старой схемы к новой.

**Миграции нумеруются и применяются строго по порядку.**\
`00001_init.sql`, потом `00002_…`, и никогда наоборот: каждая следующая рассчитывает, что предыдущие уже применены.

**База помнит, какие миграции уже применены.**\
goose хранит это в таблице `goose_db_version`, поэтому повторный запуск применяет только новые.

**Схема — это код.**\
Она лежит в репозитории, проходит ревью и версионируется вместе с кодом, который от неё зависит.

---

### Миграции у нас

**Инструмент — goose.**\
Аналоги: `golang-migrate`, `atlas`.

**Файлы лежат в `internal/infrastructure/postgres/migrations/` и встроены в бинарник через `//go:embed`.**\
`embed` — механизм Go, который вшивает файлы прямо в скомпилированную программу.

> Почему так, а не файлами рядом с бинарником, — вопрос шага 02.

**Файл миграции состоит из двух частей.**\
Что делать при применении и как откатить:

```sql
-- +goose Up
CREATE INDEX ...;      -- что делать при применении

-- +goose Down
DROP INDEX ...;        -- как откатить
```

**goose по умолчанию выполняет каждую миграцию в транзакции.**\
Если миграция упала посередине, всё, что она успела сделать, откатится.

**Некоторые команды в транзакции выполнять нельзя, например `CREATE INDEX CONCURRENTLY`.**\
Для таких файлов в начало добавляют строку `-- +goose NO TRANSACTION`.

---

### Почему миграции бывают опасными

**На пустой базе любая миграция мгновенная, на таблице в 100 миллионов строк под нагрузкой — нет.**\
То, что за секунду прошло на ноутбуке, на проде может положить сервис. Есть две вещи, которые надо знать.

#### 1. Блокировка таблицы

**Многие `ALTER TABLE` берут на таблицу самую сильную блокировку — в Postgres это `ACCESS EXCLUSIVE`.**\
Пока она держится, к таблице не может обратиться никто, даже `SELECT`.

**Хуже того: пока миграция только ждёт эту блокировку, все новые запросы к таблице встают в очередь за ней.**\
Например, миграция ждёт, пока закончится долгий отчёт. Сервис уже лежит, хотя миграция ещё даже не началась.

> **Защита:** перед опасной миграцией ставят `SET lock_timeout = '5s'`. Лучше упасть и повторить, чем положить прод.

#### 2. Перезапись или полное сканирование таблицы

**Одни изменения меняют только метаданные и выполняются мгновенно при любом размере таблицы.**\
Метаданные — это описание схемы: имена колонок, типы. Строки самой таблицы при этом не трогаются.

**Другие требуют прочитать или переписать каждую строку и всё это время держат блокировку.**\
Из пункта 1 понятно, чем это кончается на большой таблице.

#### 3. Индексы

**Обычный `CREATE INDEX` не блокирует чтение, но блокирует запись в таблицу на всё время построения.**\
На большой таблице это минуты, и все `INSERT` и `UPDATE` эти минуты ждут.

**`CREATE INDEX CONCURRENTLY` строит индекс, не блокируя запись.**\
Цена: он работает дольше и не может выполняться внутри транзакции.

> В задаче есть вопрос, что опаснее: добавить колонку или добавить колонку `NOT NULL`. Рассуждай через пункты 1 и 2: **что база должна сделать с уже существующими строками в каждом случае?**

---

### Expand / contract

**Как переименовать колонку, если старая версия сервиса ещё работает и читает старое имя?**\
При деплое старые и новые инстансы какое-то время работают одновременно, и схема должна подходить обоим.

**Изменение раскладывают на шаги, каждый из которых совместим с обеими версиями кода:**

1. **Expand (расширить):** добавить новую колонку. Код пишет в обе, читает из старой.
2. **Перенос:** скопировать старые данные в новую колонку пачками.
3. **Переключение:** код начинает читать из новой колонки.
4. **Contract (сузить):** когда старого кода нигде не осталось, удалить старую колонку.

**Долго, зато в любой момент можно откатить код без отката схемы.**\
На каждом шаге и старая, и новая версия сервиса работают со схемой без ошибок.

**Для MySQL есть инструменты онлайн-миграций gh-ost (от GitHub) и pt-online-schema-change (от Percona).**\
Многие `ALTER` в MySQL исторически блокировали таблицу. Эти инструменты создают копию таблицы с новой схемой, переносят в неё данные в фоне и в конце быстро подменяют одну таблицу другой.

## 10. Postgres vs MySQL

**Оба — зрелые OLTP-базы, и для большинства задач подходят оба.**\
Выбор между ними редко решает судьбу проекта. Ниже различия, которые реально встречаются на практике.

| | Postgres | MySQL (InnoDB) |
|---|---|---|
| Уровень изоляции по умолчанию | READ COMMITTED | REPEATABLE READ (с gap/next-key locks) |
| MVCC | старые версии в самой таблице → нужен VACUUM | старые версии в undo log → нет VACUUM, но purge и рост undo при долгих транзакциях |
| Типы данных | богатые: массивы, `JSONB` с GIN-индексами, диапазоны, `uuid`, enum, свои типы | беднее; `JSON` есть, индексы по нему — через generated columns или функциональные индексы |
| DDL в транзакции | да: несколько `ALTER` можно откатить разом | нет: каждый DDL неявно коммитит текущую транзакцию |
| Расширения | PostGIS, pg_trgm, TimescaleDB, pgvector… | плагины есть, экосистема уже |
| `INSERT … RETURNING` | да | нет (есть в MariaDB) |
| Репликация | физическая (по WAL) и логическая | binlog (statement- или row-based); исторически проще в настройке |
| Распространённость | чаще выбирают для новых проектов | огромная установленная база, особенно в вебе (WordPress, PHP-проекты, исторически Facebook, GitHub) |

---

### Пояснения к таблице

#### 1. DDL в транзакции

**DDL (Data Definition Language) — команды, меняющие схему: `CREATE`, `ALTER`, `DROP`.**\
В отличие от **DML** (Data Manipulation Language: `SELECT`, `INSERT`, `UPDATE`, `DELETE`), которые меняют данные.

**В MySQL DDL нельзя откатить вместе с транзакцией.**\
Если миграция из трёх `ALTER` упала на третьем, первые два уже применены, и откатить их автоматически нельзя.

#### 2. `RETURNING`

**`RETURNING` возвращает данные из вставленной или изменённой строки тем же запросом.**\
Например, `INSERT … RETURNING id, created_at` сразу отдаёт id и время, которые сгенерировала база.

**В MySQL для этого нужен второй запрос.**\
Сначала вставляешь, потом отдельно читаешь то, что получилось.

#### 3. Generated column

**Generated column — колонка, значение которой база вычисляет сама из других колонок.**\
Например, `sku VARCHAR(64) AS (items->>'$[0].sku')` достаёт поле из JSON.

**По ней уже можно строить обычный индекс.**\
Так в MySQL индексируют поля внутри JSON.

#### 4. Binlog

**Binlog — журнал изменений, который MySQL ведёт для репликации.**\
Реплики читают его и повторяют у себя те же изменения.

**Statement-based binlog записывает сами SQL-запросы, row-based — изменённые строки.**\
Row-based надёжнее: запрос с `NOW()` или `RAND()` на реплике может дать другой результат, а готовые строки — всегда те же.

---

### Различия в нашем коде

**Оба адаптера реализуют один и тот же порт и проходят один контракт-тест.**\
Сравни `internal/infrastructure/postgres` и `internal/infrastructure/mysql` построчно.

**Разница — в мелочах диалекта, и почти каждая из них — потенциальный баг при переносе.**\
Диалект — это особенности SQL конкретной базы: синтаксис, функции, поведение драйвера.

| Что | Postgres (pgx) | MySQL (database/sql) |
|---|---|---|
| Плейсхолдеры параметров | `$1, $2` — по номеру | `?` — по позиции |
| Передать список id | `WHERE id = ANY($1)` и `[]string` одним параметром | массивов нет: собираем `IN (?, ?, ?)` руками под длину списка |
| Ошибка «дубликат ключа» | `PgError.Code == "23505"` (SQLSTATE `unique_violation`) | `MySQLError.Number == 1062` (`ER_DUP_ENTRY`) |
| `RowsAffected()` после `UPDATE` | число **найденных** по `WHERE` строк | по умолчанию число **изменённых** строк: если новое значение совпало со старым, строка не считается. Флаг `clientFoundRows=true` в DSN переключает на найденные |
| Время | `TIMESTAMPTZ` | `DATETIME(6)`, плюс `parseTime=true&loc=UTC` в DSN |

**SQLSTATE — стандартный пятисимвольный код ошибки из стандарта SQL.**\
Postgres использует именно его, поэтому коды стабильны и документированы: [Appendix A](https://www.postgresql.org/docs/current/errcodes-appendix.html). У MySQL есть ещё и собственные числовые коды.

**DSN (Data Source Name) — строка подключения со всеми параметрами.**\
Например: `user:pass@tcp(host:3306)/db?parseTime=true&loc=UTC`.

## 11. Как Go-код ходит в базу: драйверы, ORM, query builders

**Шпаргалка раздела:**

| Уровень | Примеры | SQL пишешь сам? |
|---|---|---|
| чистый SQL + драйвер | `pgx`, `database/sql` | да — **так у нас** |
| помощник для сканирования | `sqlx`, `scany` | да |
| query builder | `squirrel`, `goqu` | собираешь из вызовов Go |
| кодогенерация из SQL | `sqlc` | да, Go-код генерируется |
| ORM | `gorm`, `ent`, `bun` | нет, SQL генерирует библиотека |

---

### Драйверы

#### `database/sql`

**`database/sql` — стандартный пакет Go, общий интерфейс над любыми SQL-базами.**\
В нём есть `QueryContext`, `ExecContext`, `Tx` и пул соединений, одинаковые для всех баз.

**Конкретную базу подключает драйвер.**\
Например, `github.com/go-sql-driver/mysql`, `lib/pq` или `pgx/stdlib`.

**Плюс — один API для всех баз. Минус — только то, что есть у всех.**\
Нет массивов и специфичных типов, а ошибки нужно разбирать через типы конкретного драйвера.

#### `lib/pq`

**`lib/pq` — исторически первый Postgres-драйвер для `database/sql`.**\
Сейчас он в режиме поддержки: ошибки чинят, а новых возможностей не добавляют.

#### `pgx`

**`pgx` — Postgres-драйвер со своим, нативным API.**\
«Нативный» значит, что API повторяет возможности самого Postgres, а не общий знаменатель всех баз.

**Он умеет всё, что умеет Postgres.**\
Массивы, `JSONB`, `COPY` для массовой вставки, `LISTEN/NOTIFY`, бинарный протокол, собственный пул `pgxpool`.

**Может работать и как драйвер для `database/sql`, если нужно.**\
Это пакет `pgx/stdlib`; через него у нас работает goose.

> Его [README](https://github.com/jackc/pgx) — хорошее чтение к 🤔-вопросу шага 02.

---

### Спектр абстракций

**От «пишу SQL руками» до «SQL не вижу вообще» — пять уровней.**\
Чем выше уровень, тем меньше кода пишешь сам, но тем меньше контролируешь, какой SQL уйдёт в базу.

1. **Чистый SQL + драйвер** (`pgx`, `database/sql`) — запросы и `Scan` пишешь сам. Так сделано у нас.
2. **Помощник для сканирования** (`sqlx`, `scany`) — раскладывает строки результата в структуры по тегам, а SQL всё ещё твой.
3. **Query builder** (`squirrel`, `goqu`) — собирает SQL из вызовов Go: `sq.Select("*").From("orders").Where(sq.Eq{"id": id})`. Удобно, когда запрос собирается динамически, например из фильтров формы.
4. **Кодогенерация из SQL** (`sqlc`) — ты пишешь `.sql`-файлы с запросами, а `sqlc` генерирует типобезопасные Go-функции и структуры. SQL полностью под контролем, бойлерплейта нет.
5. **ORM** (`gorm`, `ent`, `bun`) — описываешь структуры, а библиотека сама генерирует SQL, следит за связями, иногда и за миграциями.

---

### Что такое ORM

**ORM (Object-Relational Mapping) — библиотека, которая связывает объекты в коде с таблицами в базе.**\
Ты работаешь с объектами (`user.Orders`, `db.Save(&order)`), а ORM превращает это в SQL.

**Есть два основных стиля ORM.**\
Они отличаются тем, кто отвечает за сохранение: сам объект или отдельный компонент.

#### Active Record

**Объект сам умеет себя сохранять: `order.Save()`, `Order.find(1)`.**\
Данные и доступ к базе живут в одном классе.

> Так устроены Ruby on Rails и Laravel (Eloquent).

#### Data Mapper

**Объект ничего не знает о базе, а сохраняет и загружает его отдельный компонент.**\
Этот компонент называют маппером, репозиторием или session: `session.add(order)`.

> Так устроены Hibernate (Java) и SQLAlchemy (Python). Наш `port.OrderRepository` по духу ближе к Data Mapper, только маппинг написан руками.

---

### Проблема N+1

**Классическая ловушка ORM, но встречается и без неё.**\
Пример: нужно показать 50 заказов и имена их клиентов.

```go
orders := repo.ListRecent(ctx, 50)            // 1 запрос
for _, o := range orders {
    c := customers.Get(ctx, o.CustomerID)     // + 50 запросов, по одному на заказ
}
```

**Итого 1 + N = 51 запрос вместо одного-двух.**\
Каждый запрос быстрый, но 51 поход по сети до базы — это заметно, а на странице со списком в 1000 строк — катастрофа.

**С ORM это особенно коварно.**\
Строка `o.Customer.Name` выглядит как обращение к полю, а на самом деле незаметно делает запрос в базу. Это называют **lazy loading** (ленивая загрузка).

**Решения:**

- один запрос с `JOIN`;
- второй запрос сразу за всеми нужными клиентами: `WHERE id = ANY($1)`;
- в ORM — явная «жадная» загрузка (`Preload` в gorm).

> Что ты получаешь и теряешь с ORM и почему в этом репо её нет — вопрос шага 02, ответ пойдёт в ADR.

## 12. Надёжность и масштабирование: WAL, репликация

**Шпаргалка раздела:**

| Слово | Что значит |
|---|---|
| WAL / redo log | журнал изменений, который пишется на диск до самих данных |
| `fsync` | «гарантированно запиши на физический диск» |
| реплика | копия базы на другом сервере |
| failover | переключение на реплику, когда primary умер |
| replication lag | отставание реплики от primary |
| шардирование | разделение данных по нескольким независимым базам |

---

### WAL: как база выполняет обещание «D» из ACID

**Писать изменённые страницы таблицы на диск при каждом `COMMIT` медленно: они разбросаны по диску.**\
Пришлось бы прыгать по разным местам диска ради одной транзакции.

**Поэтому база сначала пишет короткую запись о том, что изменилось, в последовательный журнал.**\
Последовательная запись — в конец одного файла — самая быстрая операция для любого диска. Сами таблицы база обновляет позже, не спеша.

**В Postgres этот журнал называется WAL (Write-Ahead Log), в InnoDB — redo log.**\
По-русски WAL — «журнал упреждающей записи»: запись в журнал идёт впереди изменения данных.

**`COMMIT` считается успешным, когда запись о транзакции гарантированно легла на диск.**\
Для этого база вызывает **`fsync`** — системный вызов «сбрось буферы ОС на физический диск и дождись подтверждения». Без `fsync` данные могут лежать в кэше ОС и пропасть при отключении питания.

**Сервер упал — после перезапуска база проигрывает WAL и восстанавливает всё закоммиченное.**\
«Проигрывает» значит: читает журнал по порядку и применяет к таблицам изменения, которые туда не успели попасть.

#### `synchronous_commit = off`

**Это настройка Postgres «не ждать `fsync` на каждый `COMMIT`».**\
Коммиты становятся заметно быстрее, потому что не ждут диска.

**Цена: при падении сервера можно потерять последние доли секунды закоммиченных транзакций.**\
Базу это не сломает: она останется целой, просто «отъедет» чуть назад во времени.

> Иногда это приемлемая сделка (логи, метрики). Для заказов и денег — нет.

---

### Репликация

**Реплика — копия базы на другом сервере, которая постоянно получает изменения с главного.**\
Главный сервер называют **primary** (раньше говорили master).

#### Зачем нужны реплики

- **Отказоустойчивость.** Primary умер — реплику назначают новым primary. Это называется **failover**.
- **Масштабирование чтения.** Тяжёлые чтения и отчёты отправляют на реплики (**read replicas**), а primary занимается записью.

#### Как передаются изменения

**Физическая (streaming) репликация в Postgres — реплике передаётся сам WAL, байт в байт.**\
Реплика — точная копия всего сервера, только для чтения.

**Логическая репликация в Postgres — передаются логические изменения.**\
Например: «в таблице orders вставлена строка с такими значениями». Так можно реплицировать отдельные таблицы и даже в базу другой версии.

> На этом же механизме (**logical decoding**) работают CDC-инструменты вроде Debezium, см. [09-patterns](09-patterns.md).

**В MySQL реплика читает binlog primary и применяет его у себя.**\
Binlog описан в [разделе 10](#4-binlog).

#### Синхронная и асинхронная репликация

**По умолчанию репликация асинхронная: primary коммитит, не дожидаясь реплики.**\
Если primary умер сразу после коммита, последние транзакции могут не успеть доехать до реплики и пропасть при failover.

**Синхронная репликация ждёт подтверждения от реплики на каждый коммит.**\
Это надёжнее, но каждый коммит медленнее, а если реплика недоступна, запись встаёт.

#### Replication lag (отставание реплики)

**Реплика всегда немного отстаёт от primary: от миллисекунд до минут под нагрузкой.**\
Изменение сначала попадает на primary и только потом доезжает до реплики.

**Классический баг: пользователь создал заказ, а страница заказа говорит «не найден».**\
Заказ записался на primary, страница читает с реплики, а туда он ещё не доехал.

**Гарантия, которой здесь не хватает, называется read-your-writes: свои записи видишь сразу.**\
Обычное решение — читать с primary то, что пользователь только что изменил.

---

### Шардирование

**Шардирование — разделение данных по нескольким независимым базам.**\
Например, клиенты A–M в одной базе, N–Z в другой. Каждая такая база — **шард**.

**Оно масштабирует запись, но транзакции и `JOIN` между шардами становятся очень сложными.**\
Каждый шард — отдельная база, и общей транзакции у них нет.

**В Postgres и MySQL «из коробки» шардирования нет.**\
Его делают в приложении или через надстройки: Citus для Postgres, Vitess для MySQL.

> Именно поэтому для огромного потока записи смотрят в сторону баз, которые шардируются сами, — [07](07-wide-column.md).

**Самое важное для шага 02:**
