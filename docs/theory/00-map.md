# Карта инфраструктуры

Это обзор, а не погружение. Цель — чтобы при слове «ClickHouse» или «NATS» в голове сразу всплывало: **какую роль играет, на какой вопрос отвечает, с чем конкурирует**. Глубина — в файлах по ролям и в задачах.

## Главный тезис слоя

Domain и Use Case знают только **интерфейсы** (порты). Инфраструктура — это **реализации** этих интерфейсов. Направление зависимостей одно:

```
internal/infrastructure/postgres  ──imports──▶  internal/app/port, internal/app/domain
internal/app/usecase              ──imports──▶  internal/app/port, internal/app/domain
internal/app/domain               ──imports──▶  (только stdlib)
```

В этом репо тезис проверяется руками: одни и те же контракт-тесты гоняются против memory, Postgres, MySQL и Mongo; один и тот же сценарий e2e — против всех комбинаций хранилищ и брокеров. Если use case заметил подмену — дизайн сломан.

## Как выбирать: вопросы, которые стоит задать до технологии

Прежде чем сказать «возьмём Kafka», ответь на вопросы ниже. Ответы почти всегда сужают выбор до 1–2 вариантов.

1. **Что будет источником истины?** Если данные потерять нельзя — это транзакционная база. Всё остальное (кэш, поиск, аналитика) должно уметь восстановиться из неё.
2. **Какая форма запросов?** Точечно по ключу? Диапазоны? Полнотекст? Агрегаты по миллиардам строк? Разные формы — разные хранилища.
3. **Какое соотношение чтений и записей?** И какие объёмы — сотни RPS или сотни тысяч?
4. **Какая консистентность нужна?** Пользователь должен видеть свою запись сразу (read-your-writes) или допустимо «через секунду»?
5. **Что будет при отказе?** Компонент упал — система деградирует или встаёт целиком?
6. **Кто будет это эксплуатировать?** Kafka-кластер, Elasticsearch-кластер, Cassandra-кластер — это отдельная работа. «Ещё одна технология» — это всегда ещё одна вещь, которая будит ночью.

## Матрица «по умолчанию»

Не догма, а стартовая точка для типичного бэкенда:

- **Начни с Postgres.** Он закрывает 80% задач: транзакции, JSONB, полнотекст (`tsvector`), очереди (`SKIP LOCKED`), даже простую аналитику. Новую технологию добавляй, когда упёрся в конкретное ограничение, и запиши это ограничение в ADR.
- **Кэш** — когда профилирование показало горячие чтения, а не «на всякий случай».
- **Брокер** — когда появился второй потребитель изменений или нужно развязать сервисы по времени.
- **Поиск** — когда `ILIKE '%...%'` и `tsvector` перестали устраивать по качеству или скорости.
- **Аналитика** — когда отчёты по OLTP-базе начали мешать продакшен-трафику.
- **Wide-column** — когда запись упёрлась в один узел и шардирование руками стало болью.

## 🔎 Изучи сам

Термины, которые встретятся во всех файлах. Без объяснений — найди и разберись:

- OLTP vs OLAP
- ACID, BASE
- CAP-теорема, PACELC
- read-your-writes, eventual consistency, linearizability
- write amplification, read amplification
- B-tree vs LSM-tree
- горизонтальное vs вертикальное масштабирование, шардирование, репликация
- hexagonal architecture (ports & adapters), clean architecture, dependency inversion

Первоисточники:

- Martin Kleppmann, *Designing Data-Intensive Applications* — главы 1–3, 5–7, 11. Если читать одну книгу по теме, то эту.
- Alistair Cockburn, [Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/)
- [Jepsen](https://jepsen.io/analyses) — как базы и брокеры на самом деле ведут себя при сбоях **(это читать необязательно, только если хочется узнать, как ломаются системы; отчёты местами старые)**
