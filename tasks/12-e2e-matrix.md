# 12 — E2E: оркестратор на матрице конфигураций 🟠

## Цель

Доказать главный тезис раздела прямо тестом: одни и те же сценарии use case'ов проходят на **любой** комбинации хранилища и брокера.

## Теория

- [10-testing](../docs/theory/10-testing.md): E2E-матрица

## Что дано

- `test/e2e/harness` — сборка приложения из реальных адаптеров (`Build`), ленивые контейнеры (`Infra`), реестр фабрик (`Register*`), раннер матрицы (`RunMatrix`), `Recorder`, `Eventually`
- фабрики для memory, Postgres, MySQL, Mongo, RabbitMQ, Redis Streams, Kafka
- `test/e2e/e2e_test.go` — один пример сценария

## 🤔 Подумай до кода

1. Матрица 4 хранилища × 4 брокера = 16 стеков × N сценариев. Сколько это займёт времени? Что запускать на каждый PR, а что — по кнопке?
2. Почему сценарии проверяют события через `Eventually`, а не сразу?
3. Почему каждый тест получает свою базу/топик, а не общий?
4. Сценарий проходит на `postgres+kafka` и падает на `mongo+nats`. Как найти, кто виноват?
5. Какие свойства системы стоит проверить именно на e2e, а не контрактом адаптера?

## Что сделать

1. `test/e2e/factories_test.go`: зарегистрируй свои адаптеры — `RegisterBroker("nats", …)`, `RegisterCache("redis", …)`, `RegisterProjection("search", …)`, `RegisterProjection("analytics", …)`.
2. `test/e2e/scenarios_test.go`: добавь сценарии в `scenarios` (через `init()`). Минимум:
   - полный цикл place → pay → cancel даёт три события с версиями 1, 2, 3;
   - недопустимый переход не порождает события;
   - конкурентная оплата одного заказа: ровно одна успешная, одно событие `OrderPaid`;
   - с кэшем: `Get` после `Pay` видит `paid`;
   - с проекциями: поиск и аналитика догоняют.
3. Прогони всю матрицу. Если что-то падает только на одном стеке — найди причину и, если это дыра в контракте, допиши контракт-тест.

## ✅ Definition of Done

```sh
make check
make e2e                  # вся матрица зелёная, SKIP нет
```

Для отладки: `E2E_STORES=postgres E2E_BROKERS=kafka make e2e`.
