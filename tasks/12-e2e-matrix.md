# 12 — E2E: оркестратор на матрице конфигураций 🟠

> **Уровень 🟠 — половина.** Дан каркас: сборка приложения, контейнеры, раннер матрицы, один пример сценария.\
> Свои адаптеры и сценарии добавляешь ты. Что значат уровни — в [README задач](README.md#лестница).

## Цель

**Доказать главный тезис раздела прямо тестом.**\
Тезис: адаптеры взаимозаменяемы, и use case'ам всё равно, на чём они работают ([00-map, раздел 1](../docs/theory/00-map.md#1-главный-тезис-слоя)).

**Одни и те же сценарии use case'ов проходят на любой комбинации хранилища и брокера.**\
Комбинация — например, Postgres + Kafka или Mongo + NATS. Все комбинации вместе — матрица ([10-testing, раздел 7](../docs/theory/10-testing.md#7-e2e-матрица)).

## Что дано

| Где | Что внутри |
|---|---|
| `test/e2e/harness` | сборка приложения из реальных адаптеров (`Build`), ленивые контейнеры (`Infra`), реестр фабрик (`Register*`), раннер матрицы (`RunMatrix`), `Recorder`, `Eventually` |
| `test/e2e/harness/factories.go` | фабрики для memory, Postgres, MySQL, Mongo, RabbitMQ, Redis Streams, Kafka |
| `test/e2e/e2e_test.go` | один пример сценария и `TestMatrix` |

**Фабрика — функция, которая по контейнеру создаёт готовый адаптер для теста.**\
Например, `PostgresStore(t, inf)` берёт у `Infra` адрес Postgres и возвращает готовое хранилище. Фабрики регистрируются по имени: `RegisterStore("postgres", PostgresStore)`.

**Ленивые контейнеры — стартуют при первом обращении, один раз на весь запуск тестов.**\
Если в матрице нет Kafka, контейнер Kafka вообще не поднимется.

**`Recorder` — подписчик, который запоминает все доставленные события.**\
`rec.Of(orderID)` возвращает события одного заказа без дубликатов, в порядке доставки.

## Что сделать

#### 1. Зарегистрируй свои адаптеры

**Создай `test/e2e/factories_test.go` и в `init()` зарегистрируй адаптеры, сделанные в прошлых шагах:**

- `RegisterBroker("nats", …)` — шаг 09;
- `RegisterCache("redis", …)` — шаг 05;
- `RegisterProjection("search", …)` — шаг 10;
- `RegisterProjection("analytics", …)` — шаг 11.

**`init()` — функция Go, которая выполняется автоматически при загрузке пакета, до тестов.**\
Поэтому регистрация в `init()` срабатывает раньше, чем `TestMatrix` начнёт перебирать стеки.

**Образец — `test/e2e/harness/factories.go`.**\
Там уже зарегистрированы memory, Postgres, MySQL, Mongo, RabbitMQ, Redis Streams и Kafka.

> ⚠️ Первая строка обоих новых файлов — `//go:build e2e`, как в `e2e_test.go`. Без тега файл не соберётся вместе с harness: у пакета `harness` стоит тот же тег.

#### 2. Добавь сценарии

**Создай `test/e2e/scenarios_test.go` и добавь сценарии в `scenarios` через `init()`.**\
`scenarios` — срез `[]harness.Scenario` из `e2e_test.go`. В `init()` к нему дописывают свои через `append`.

**Минимум пять сценариев:**

1. полный цикл place → pay → cancel даёт три события с версиями 1, 2, 3;
2. недопустимый переход не порождает события;
3. конкурентная оплата одного заказа: ровно одна успешная, одно событие `OrderPaid`;
4. с кэшем: `Get` после `Pay` видит `paid`;
5. с проекциями: поиск и аналитика догоняют.

**Сценарию с кэшем или проекциями нужен другой стек — для этого поле `Stack`.**\
Это функция, которая получает базовый стек матрицы и возвращает изменённый — например, с добавленным кэшем `redis`.

**«Не порождает события» — значит, события нет и через какое-то время.**\
Проверить отсутствие сложнее, чем наличие: нельзя ждать «пока не придёт». Подумай, после какого события можно быть уверенным, что лишнего уже не будет.

#### 3. Прогони всю матрицу

```sh
make e2e
```

**Если что-то падает только на одном стеке — найди причину.**\
Если это дыра в контракте, допиши контракт-тест, чтобы такое расхождение ловилось уже на уровне адаптера.

## ✅ Definition of Done

```sh
make check
make e2e                  # вся матрица зелёная, SKIP нет
```

**Для отладки матрицу сужают переменными окружения:**

```sh
E2E_STORES=postgres E2E_BROKERS=kafka make e2e
```
